# 小哈工单智能诊断助手 改造技术方案

> 基于差旅出行助手 Multi-Agent 框架改造，面向 B 端商户工单智能诊断场景

---

## 一、项目定位与叙事线

### 1.1 做什么

一个基于自研 Multi-Agent 编排框架的 **小哈工单智能诊断助手**——基于 RAG 的商户投诉快速定位系统。针对商户投诉工单实现自动化的问题定位、日志追踪、根因分析和归属方判定，将前端+后端联合排查半小时的流程压缩到 12 秒。

诊断助手的使用者是 **接到工单的那个第一响应人**，不管他是前端还是后端。他在用诊断助手帮他做信息收集和三方路由——而不是自己打开三个平台去查。

### 1.2 业务痛点来源（你在哈啰的真实观察）

> 我在哈啰做资产和商户中后台时，发现一个高频痛点：商户投诉进来后，前端和后端要拉会一起排查工单。查前端代码有没有 bug、查后端接口日志是否正常、查生产环境是否有脏数据混入。一次典型的"这个订单为什么状态不对"的工单，前后端各查各的，半小时才能定位责任方——是代码问题？用户操作失误？还是数据被线上脚本误改了？
>
> 三个角色的排查路径完全不同，但经常是三个人在同一个工单上重复劳动。我就想，能不能用一个 Agent 来同时走这三条排查路径，自动给出诊断结论和归属判定。

**业务场景**：

```
真实场景：
  商户投诉工单进来 → 谁来接？
  
  大公司：有专门的 on-call/support 轮值同学（可能是前端、可能是后端，轮流当值）
  小公司/小团队：谁有空谁接
  
  这个人接到工单后的第一反应不是"我来修"，
  而是"我得先搞清楚这他妈是谁的锅"。
```

### 1.3 用户画像

| 角色 | 做什么 | 诊断助手帮他省了什么 |
|------|--------|-------------------|
| 工单第一响应人（可能是前端，可能是后端） | 接工单 → 查信息 → 判定归属 → 转给对应方 | **不用同时开监控面板+日志平台+数据库三个窗口了** |
| 客服/技术支持 | 商户投诉过来了，需要给商户一个初步回复 | 不用等开发查完再回复，Agent 先给个初步判断 |
| 研发 on-call | 半夜被报警叫起来，脑子不清醒 | Agent 已经把三条路径并行跑完了，结论放在面前 |

**面试话术（业务价值）**：

> "这个工具的使用者不是某个具体角色。在哈啰，商户投诉工单进来后，会随机派给 on-call 同学——有时候是前端接到，有时候是后端。不管谁接到，都要做同样的事：打开三个平台各自查一遍再找人。Agent 让这件事变成一键式的。它不是完全替代人工，而是让第一响应人不再需要同时开三个窗口反复切换。Agent 负责把散落的线索收集并初步分析，人负责做最终判断和修复。"

### 1.4 为什么适合前端背景

|------------------------|-------------------|
| 运维指标采集、CMDB、基础设施——实际没碰过 | **商户工单、订单状态、退款流程——在资产商户中后台天天见** |

### 1.5 技术叙事

> 我在小哈换电做资产和商户中后台时，观察到商户投诉工单的排查流程存在大量重复劳动——前端查 UI 状态、后端查接口日志、数据侧查数据一致性，三拨人各自查半小时再对答案。后来我做 Multi-Agent 编排框架时就想，这个场景天然适合 Agent 并行调度：让三个诊断 Agent 同时跑三条排查路径，最后汇总出诊断结论和责任归属。
>
> 底座自研了 Multi-Agent 框架（IntentionAgent + OrchestrationAgent + LazyAgentRegistry + 双层记忆 + 弹性机制），但在诊断场景里没有走完全自由式 Agent，而是采用 **受控多 Agent** 设计：上层保留 IntentionAgent、OrchestrationAgent、LazyAgentRegistry 的通用多 Agent 玩法，下层把商户管理、经营、结算三大业务域抽象成 30 个原子 Skill，由 CodeAgent、OperationAgent、DataAgent、ResolutionAgent 在各自职责边界内调用 Skill 完成排查。这样既继承了 Aligo 的通用多 Agent、LLM 驱动、Skill 插件化架构，又保留了工单诊断需要的稳定性和准确度。前端背景体现在自研的诊断 Trace 面板——实时展示多 Agent 并行推进和交叉验证过程。

### 2.3 Skill 设计哲学

遵循 **原子化 + 可组合 + 可观测** 原则：

| 原则 | 说明 | 体现 |
|------|------|------|
| **原子化** | 每个 Skill 只做一件事，输入输出明确 | 30 个 Skill 各对应单一数据源，职责边界清晰 |
| **可组合** | 通过多 Agent + Skill 组合完成复杂诊断 | Agent 负责视角拆分，Skill 负责精细查询，如 CodeAgent 组合 TraceRequestLog + GetBillingConfig |
| **可观测** | 每个 Skill 执行过程可追踪、可解释 | TraceCollector 全链路追踪 + 前端面板实时展示 |

### 2.4 Agent 与 Skill 分层

为避免工单诊断场景下“完全自由式 Agent”带来的漂移，系统采用 **受控多 Agent** 架构：

- **通用多 Agent 层**：保留 Aligo 的 `IntentionAgent + OrchestrationAgent + LazyAgentRegistry`，负责意图识别、Agent 调度、懒加载与多轮协作
- **专业诊断 Agent 层**：引入 `CodeAgent / OperationAgent / DataAgent / ResolutionAgent`
- **原子 Skill 层**：每个 Agent 在职责边界内调用原子 Skill，不直接跨域自由发散
- **Tool 层**：由 `ToolRegistry` 统一封装 mock 数据、日志查询、知识库检索等数据源

这样做的好处是：

1. 保持 Aligo 原有的通用多 Agent、LLM 驱动、Skill 插件化架构
2. 让每个 Agent 只在自己的专业边界内行动，提升诊断稳定性
3. 保留开放式自然语言入口与可扩展能力，未来可以继续接入新的 Agent 与 Skill

### 2.6 与 Aligo 原工程的关系

这套方案与 Aligo 原本旅行类工程的关系，建议表述为：

- **复用的部分**：`IntentionAgent -> OrchestrationAgent -> LazyAgentRegistry` 的分层思路、priority 并行调度、记忆系统、重试熔断、结构化输出兜底、trace/日志等通用底座能力
- **适配改造的部分**：诊断主入口、专业 Agent 角色、领域记忆模型、30 个诊断原子 Skill、RAG 知识库内容、CLI/API/Web 的产品化外壳
- **结论**：这不是“Aligo 底层框架基本不动”的轻量改动，而是基于通用多 Agent 底座做的一次诊断域迁移，改动量属于中等，重点在主链路和领域模型适配，而不是推翻底层编排思想重做

## 三、Agentic Loop 设计

### 3.1 为什么工单诊断天然适合多轮 Loop

- **第一轮不够**：一个工单信息可能不全（"订单状态不对"——哪个订单？什么状态？），需要先解析再补充
- **多 Agent 并行后需要交叉验证**：CodeAgent 说链路没问题、DataAgent 说存在状态冲突、OperationAgent 说用户未误操作，这时需要 ResolutionAgent 汇总证据后再归因
- **归属判定不是一次性能做的事**：需要三条路径都跑完才能下结论是谁的责任

### 3.2 流程时序

```
用户: "工单 WO-20260815-0421，商户2037反馈订单ORD-8823状态异常"
    │
    ▼
┌─ Loop Round 1: 信息收集 ─────────────────────────────────────┐
│  IntentionAgent → intent: "ticket_diagnosis"                  │
│  OrchestrationAgent → priority=1 并行调度基础信息 Agent:       │
│    ├─ CodeAgent       → GetOrderDetail / GetOrderTimeline      │
│    ├─ OperationAgent  → GetMerchantProfile / SearchHistoryTicket│
│    └─ DataAgent       → 预加载订单与商户关键实体                │
│  产出: {商户:2037, 订单:ORD-8823, 问题:状态异常,              │
│          当前状态:待退款, 应为:已退款}                          │
│  LoopDecider → "continue"（信息齐全，启动三条排查路径）        │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Loop Round 2: 三条排查路径并行 ──────────────────────────────┐
│  IntentionAgent → intent: "deep_diagnosis"                    │
│  OrchestrationAgent → priority=1 多 Agent 并行:                │
│                                                                │
│  🔴 CodeAgent: 代码问题排查（前后端视角）                       │
│  → TraceRequestLog 追踪退款接口调用链                          │
│  → GetBillingConfig 检查功能开关/灰度配置                      │
│  → 输出: "退款接口正常返回200，无代码异常"                      │
│                                                                │
│  🟡 OperationAgent: 用户操作排查（中后台视角）                  │
│  → ReconstructTimeline 重建事件序列对比标准业务流程             │
│  → GetOrderRefund 核实退款记录                                  │
│  → 输出: "用户操作流程符合规范，非操作失误"                     │
│                                                                │
│  🟢 DataAgent: 数据一致性排查（数据视角）                       │
│  → [Tool: check_data] 对比订单表 vs 支付表 vs 结算表           │
│  → 输出: "支付表=已退款，订单表仍=待退款——数据不一致！"         │
│                                                                │
│  LoopDecider → "cross_verify"（数据路径发现异常 → 交叉验证）   │
└───────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ Loop Round 3: 交叉验证 + 归属判定 ───────────────────────────┐
│  IntentionAgent → intent: "cross_validate_and_resolve"        │
│  OrchestrationAgent → 先并行补充证据，再调 ResolutionAgent     │
│    ├─ CodeAgent / OperationAgent / DataAgent 补充交叉证据       │
│    ├─ SearchPolicyFAQ → RAG 检索"订单状态不一致"相关处理经验     │
│    └─ ResolutionAgent → 汇总证据并生成归属判定                  │
│                                                                │
│  交叉验证结果：                                                 │
│    - 代码排查: 正常 ✅                                         │
│    - 操作排查: 正常 ✅                                         │
│    - 数据校验: 异常 ⚠️（订单表≠支付表）                         │
│    - RAG 检索: 命中同类脚本 Bug                                 │
│    - ResolutionAgent: 汇总结论并排除前后端问题 ✅               │
│  → 归属判定: 数据侧（后台脚本）                                  │
│  → 处理建议: ① 手动修复 ORD-8823 订单状态                      │
│              ② 排查脚本死锁问题（同批次影响3个订单）            │
│              ③ 建议脚本增加失败重试+告警机制                    │
│                                                                │
│  LoopDecider → "done"                                          │
└───────────────────────────────────────────────────────────────┘
```

### 3.3 为什么这比简单的 ReAct 更好

| ReAct（单 Agent 串行调用 Tool） | 本项目（受控多 Agent） |
|---|---|
| 一个 Agent 自己想、自己调 Tool，容易串行阻塞 | CodeAgent / OperationAgent / DataAgent 可并行收集证据 |
| Tool 选择自由度太高，诊断场景容易跑偏 | 每个 Agent 只在自己的职责边界内调用 Skill |
| 没有天然的多视角交叉验证 | ResolutionAgent 基于多 Agent 证据做归因 |
| 更适合开放式任务探索 | 更适合垂直诊断场景下的稳定、高准确度排查 |

### 3.4 关键代码改动

```python
# agents/loop_decider.py (新增, ~50行)
class LoopDecider:
    def decide(self, round_result: dict, round_num: int) -> str:
        if round_num == 1:
            # Round 1: 信息不足则 need_info，否则 continue
            if self._missing_info(round_result):
                return "need_info"
            return "continue"

        if round_num == 2:
            # Round 2: 数据路径发现异常 → cross_verify
            if self._data_inconsistency(round_result):
                return "cross_verify"
            return "done"

        if round_num == 3:
            # Round 3: 交叉验证完成 → done
            return "done"
```

## 四、三类专业 Agent 设计（核心差异化能力）

### 4.1 CodeAgent — 代码/技术链路问题排查（🔴）

```
排查视角：前后端代码有没有 Bug？
涉及原子 Skill: TraceRequestLog, GetBillingConfig, ValidateFrontendState

Step 1: TraceRequestLog 追踪退款接口调用链
  → POST /api/refund/callback → 响应码: 200 OK
  → 耗时: 230ms，在正常范围

Step 2: GetBillingConfig 检查功能开关/灰度配置
  → 退款功能开关: ON
  → 灰度配置: 未命中该商户 => 走默认逻辑

结论: 代码侧无异常 ✅
```

### 4.2 OperationAgent — 用户操作排查（🟡）

```
排查视角：是不是用户操作失误？
涉及原子 Skill: ReconstructTimeline, GetOrderRefund, SearchHistoryTicket

Step 1: ReconstructTimeline 重建事件序列，分析用户操作轨迹
  → 用户操作序列: 提交退款 → 上传凭证 → 确认

Step 2: GetOrderRefund 核实退款记录，对比标准业务流程
  → 用户步骤符合标准退款流程
  → 凭证截图名称、格式符合要求

结论: 用户操作符合规范 ✅
```

### 4.3 DataAgent — 数据一致性排查（🟢）

```
排查视角：生产数据有没有脏数据？
涉及原子 Skill: GetOrderDetail, GetOrderTimeline, TraceRequestLog, ReconstructTimeline

Step 1: [Tool: check_data] 跨表对比
  → 订单表(order_main): status=pending_refund
  → 支付表(payment_records): status=refunded
  → 结算表(settlement_records): status=pending
  ⚠️ 支付表已退款但订单表未同步更新

Step 2: TraceRequestLog 查支付回调日志
  → 支付回调: success (14:32:15)
  → 订单更新回调: timeout (14:32:18) ← 死锁重试耗尽

Step 3: ReconstructTimeline 聚合多源日志重建完整事件序列
  → 14:32:15 支付完成 → 14:32:18 回调超时 → 状态未同步

结论: 数据不一致 ⚠️ — 支付回调成功但订单状态更新脚本死锁失败
```

### 4.4 ResolutionAgent — 交叉验证与归属判定（🔵）

```
职责：不直接做大规模数据查询，而是汇总 CodeAgent / OperationAgent / DataAgent 的证据。

Step 1: 汇总三类 Agent 的结构化输出
  → 代码链路：正常
  → 用户操作：正常
  → 数据校验：异常

Step 2: 补充外部证据
  → SearchPolicyFAQ 命中同类脚本问题
  → SearchHistoryTicket 检索到相似历史工单

Step 3: 做最终归属判定
  → 前端代码：排除
  → 后端接口：排除
  → 数据脚本：确认

输出：根因、责任归属、处理建议
```

### 4.5 面试话术

> "这个项目不是完全自由式的 Agent 聊天，而是受控多 Agent。上层采用多 Agent 架构：IntentionAgent 识别意图，OrchestrationAgent 并行调度 CodeAgent、OperationAgent、DataAgent路径排查，最后由 ResolutionAgent 汇总结论。下层每个 Agent 都是通过原子 Skill 去查自己的数据源。这样既有多 Agent 的协作感和可扩展性，又不会因为自由度过高影响诊断准确度。"

Tool Registry 作为原子 Skill 与数据源之间的适配层，将 30 个原子 Skill 对应的数据查询统一封装为可被 OrchestrationAgent 调度的诊断工具。

### 7.1 核心诊断工具

| `query_order` | 查询订单状态、支付记录、退款流水 | `GetOrderDetail`, `GetOrderTimeline`, `GetOrderRefund` | Mock JSON 订单数据 |

| `query_settlement` | 查询账单、结算、对账数据 | `GetBillDetail`, `GetSettlementStatus`, `GetReconciliation` | Mock JSON 结算数据 |
| `trace_api` | 查询指定接口在指定时间段的调用日志 | `TraceRequestLog` | Mock API 日志 |

```python
# 子 Agent 内部调用 Tool Registry
async def diagnose(self, context):
    # LLM 决策: "我需要查订单ORD-8823的状态和支付记录"
    tool_result = await ToolRegistry.execute("query_order", order_id="ORD-8823")

    # 将结构化 Tool 结果注入 LLM Prompt
    prompt = f"""
    订单查询结果: {tool_result}
    API 调用链: {trace_result}
    请判断根因和归属方。
    """
    return await self.llm.generate(prompt)
```

## 十三、面试话术框架（3 分钟版）

"我准备了一个小哈工单智能诊断助手项目。

痛点来源是我在哈啰做资产和商户中后台时的真实观察：商户投诉工单进来后，前端查代码、后端查日志、数据侧查一致性，三方各自排查半小时再对答案。我当时就想，这三条排查路径能不能并行化、自动化。

底座是自研的 Multi-Agent 编排框架：IntentionAgent 做意图识别和 Agent/Skill 路由，OrchestrationAgent 按 priority 分组并行调度，LazyAgentRegistry 做插件化加载。相较 Aligo 原本旅行工程，我复用了这些通用编排骨架，但不是框架代码一行没改的直接复用，而是在主入口、专业诊断 Agent、领域记忆模型和产品外壳上做了诊断域适配。

核心设计是三条排查路径，codeAgent、并行——代码侧排查 API 调用链和配置、操作侧对比标准业务流程、数据侧做跨表一致性校验。三条路径同时跑，跑完后在 Loop 的第三轮做交叉验证，最后给出诊断结论和归属判定。这比传统的人工串行排查效率高很多。

Skill 设计上，我按商户管理、经营、结算三大业务域抽象了 30 个原子 Skill（25 业务 + 5 通用辅助），每个 Skill 对应单一数据源。比如 GetMerchantContract 查合同档案表、GetAssetAllocation 查资产分配明细表、TraceRequestLog 查接口调用链路、ReconstructTimeline 做多源日志聚合。调度上不是完全自由式组合，而是由 CodeAgent、OperationAgent、DataAgent 在职责边界内受控调用这些 Skill，比如订单支付异常场景里，CodeAgent 负责链路与配置排查，DataAgent 负责一致性校验，最后由 ResolutionAgent 汇总完成诊断闭环。核心验证了 3 个高频场景涉及 8-10 个核心 Skill，剩余 Skill 是基于业务抽象的模式设计。
