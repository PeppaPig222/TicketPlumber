# 小哈工单智能诊断助手 — 开发手记

> 记录项目改造过程中有价值的设计决策、迭代优化思路，以及踩过的坑和解决方案。
> 面向对象：后续维护者、面试复盘、自己回头查。

---

## 一、项目改造背景

项目最初是打算设计为一个"受控多 Agent"工单诊断 demo，准确度高但架构偏 workflow runner。改造目标是在保留诊断能力的前提下，逐步回归 通用多 Agent / Skill 插件化主链路：

```
CLI/API -> IntentionAgent -> OrchestrationAgent -> LazyAgentRegistry -> 专业 Agent -> Skill
```

改造遵循两个原则：

1. **最小改动**：尽量在原有结构上扩展，不推倒重来。
2. **可验证**：每批改动都补测试、跑回归，保证 3 个高频场景闭环不降级。

## 二、Batch 1：多 Agent 角色层落地

### 2.1 专业 Agent 插件化

把 `CodeAgent / OperationAgent / DataAgent / ResolutionAgent` 从 `agents/` 硬编码实现迁移到 `.claude/skills/` 下的独立 skill 目录，每个目录包含：

- `SKILL.md`：职责说明
- `script/agent.py`：插件入口，从 `agents.xxx_agent` 导入真实实现

**为什么这么做**：

- 让 `LazyAgentRegistry` 成为主链路的一部分，符合 Aligo "Skill 即能力单元"的设计。
- 后续新增 Agent 只需新建 skill 目录，不用改 `DiagnosisService`。

### 2.2 遇到的坑：PascalCase 调度名 vs kebab-case 目录名

`OrchestrationAgent` 里调度用的是 `"CodeAgent"`，但 skill 目录名是 `"code-agent"`，导致 `LazyAgentRegistry.__getitem__` 找不到 Agent。

**解决方案**：在 `LazyAgentRegistry` 中增加 `_agent_alias_mapping`：

```python
self._agent_alias_mapping = {
    "CodeAgent": "code-agent",
    "OperationAgent": "operation-agent",
    "DataAgent": "data-agent",
    "ResolutionAgent": "resolution-agent",
}
```

并调整 `_resolve_agent_name` 优先级：skill 目录名 > 专业 Agent 别名 > legacy mapping > custom_factories。

### 2.3 依赖注入：agent_kwargs

`LazyAgentRegistry` 支持通过 `agent_kwargs` 给 skill Agent 注入依赖（如 `skill_registry`、`rag_agent`）。

```python
agent_registry = LazyAgentRegistry(
    model=None,
    cache={},
    memory_manager=memory_manager,
    agent_kwargs={
        "skill_registry": self.skill_registry,
        "rag_agent": self.rag_agent,
    },
)
```

关键点：`_load_from_skill` 里用 `inspect.signature(agent_class.__init__)` 判断是否接受某个 kwarg，只注入匹配的参数，避免不同 Agent 构造函数不一致导致报错。

## 三、Batch 5：正式 RAG 知识库

### 3.1 设计目标

把 `knowledge_base.json` 的 keyword 检索升级为基于向量库的正式 RAG，并且接入诊断主链路：

- `IntentionAgent`：规则识别失败时，用 RAG fallback 推断 scenario。
- `ResolutionAgent`：归属判定阶段，用 RAG 补充证据链。
- `DiagnosisService`：统一管理 `RAGKnowledgeAgent` 实例。

### 3.2 为什么 RAG Agent 不直接改 `tool_registry.search_kb`

考虑过把 `tool_registry` 里的 `search_kb` 直接换成向量检索，但最终没这么做：

- `tool_registry` 定位是轻量工具注册中心，底层 mock 数据源。
- RAG 依赖 pymilvus + sentence-transformers，初始化较重，失败时不应阻断 tool_registry 其他工具。
- 由 `DiagnosisService` 统一创建并注入给需要的 Agent，更符合"外部能力可插拔"的设计。

结果是：RAG 可用时用 RAG，RAG 不可用时规则链路仍然完整运行。

### 3.3 PDF 复杂架构图的处理

用户只有一份商户 PDF，且**几乎全是架构图**，`pdfplumber.extract_text()` 基本提取不到成段文字。

如果简单处理，每个图页只生成一句 `"[架构图：第 X 页，无法提取]"`，向量库里就是一堆没有信息量的 chunk，检索时根本匹配不到。

**优化策略**：

1. **多维度检测图页**：字数少、检测到 `page.images`、绘制元素（线/矩形/曲线）多，都视为图页。
2. **提取图上文字碎片**：用 `extract_words()` 捞出模块名、标签、箭头文字，按 y 坐标分行整理。
3. **上下文关联**：把图页和前后相邻页的标题/关键词拼进占位 chunk，提升可检索性。
4. **预留 OCR 扩展点**：chunk 里提示"建议后续通过 OCR 或人工标注补充"，当前不引入新依赖。

占位 chunk 示例：

```
[架构图/流程图：第 12 页]
来源文档：merchant_architecture.pdf
图上可识别的系统组件/关键词：结算中心, 分润比例, 商户标签, 结算规则
图上文字碎片：
  - 结算中心 -> 商户标签 -> 分润比例
相邻页上下文：
  - 第11页：订单支付与退款流程；关键词：支付网关, 退款回调, 订单状态
  - 第13页：资产分配与保护期；关键词：资产池, 保护期, 跨商户分配
说明：本页主要内容来自复杂架构图/流程图，文本无法完整自动提取。建议后续通过 OCR 或人工标注补充完整流程说明。
```

实际效果：初始化后 37 个 chunks 全是架构图占位，但测试检索仍能命中相关页码。

### 3.4 遇到的坑

#### 坑 1：Milvus Lite URI 格式

`RAGKnowledgeAgent` 原来用：

```python
self.milvus_client = MilvusClient(uri=f"file:{milvus_db_path}")
```

在不同环境（base conda / .venv）下表现不一致：

- 有时报错 `Open local milvus failed, dir: ... not exists`
- 有时报错 `database 'private' does not exist`

**原因**：`pymilvus 2.6.9` 会把 `file:/path` 解析出 `db_name='private'`（路径第一段）。

**解决方案**：去掉 `file:` 前缀，并显式指定 `db_name="default"`：

```python
self.milvus_client = MilvusClient(uri=milvus_db_path, db_name="default")
```

重连逻辑也要同步改：

```python
self.milvus_client = MilvusClient(self._milvus_db_path, db_name="default")
```

#### 坑 2：`milvus_lite.db` 变成了目录

删除重建时，如果 `data/rag_knowledge/milvus_lite.db` 已经是一个目录，再运行初始化会直接失败。

**原因**：Milvus Lite 在当前版本下会把 `.db` 路径作为一个数据目录使用。如果之前旧代码用 `file:` 前缀写坏了，或者手动创建过目录，就会冲突。

**解决方案**：

```bash
rm -rf data/rag_knowledge/milvus_lite.db
python scripts/init_diagnosis_kb.py --reset
```

#### 坑 3：`await self.milvus_client.has_collection()`

`_ensure_connection` 里原来这么写：

```python
await self.milvus_client.has_collection(self.collection_name)
```

但 `has_collection` 是**同步方法**，await 一个 `bool` 会抛：

```
object bool can't be used in 'await' expression
```

每次连接检查都被误判为断开，触发无意义重连，日志刷屏。

**解决方案**：去掉 `await`：

```python
self.milvus_client.has_collection(self.collection_name)
```

#### 坑 4：空文档也生成占位 chunk

最初只要页面字数少于阈值就生成图占位 chunk，导致纯空白 txt 也会生成 `"[架构图/流程图：第 1 页]"`。

**解决方案**：在 `process_document` 开头判断整份文档是否没有任何有效文本，是则直接返回空列表：

```python
total_text = "\n".join(p.get("text", "") for p in pages).strip()
if not total_text and not any(p.get("is_diagram") for p in pages):
    return []
```

#### 坑 5：`pytest-asyncio` 装饰器缺失

`tests/test_intention_agent.py` 里的测试函数是 `async def`，但没加 `@pytest.mark.asyncio`，pytest 直接报错：

```
async def functions are not natively supported.
```

**解决方案**：补装饰器和 `import pytest`。

### 3.5 RAG fallback 的阈值保护（收口时补充）

最初 IntentionAgent 的 RAG fallback 是无条件触发的：只要规则识别为 `generic_ticket_diagnosis`，就会用 RAG 结果重新推断 scenario。

但当前商户 PDF 几乎全是架构图，RAG 检索相似度只有 0.5 左右。如果无条件采纳，低质量检索反而可能把 generic 错判成具体场景，**降低准确率**。

**解决方案**：在 `config.RAG_CONFIG` 中增加开关和阈值：

```python
RAG_CONFIG = {
    "embedding_model": "data/models/bge-small-zh-v1.5",
    "enable_intention_fallback": True,
    "enable_resolution_evidence": True,
    "min_similarity_threshold": 0.55,
}
```

- `IntentionAgent`：只有 top1 相似度 ≥ 0.55 时才采纳 RAG 推断，否则保持 `generic_ticket_diagnosis`。
- `ResolutionAgent`：通过 `enable_resolution_evidence` 控制是否补充证据。
- kb_hints 仍可保留在 key_entities 中，用于 reasoning 参考，但不改变 scenario。

这样既保留了完整 RAG 框架，又避免低质量检索干扰现有规则链路。

## 四、记忆系统的三层结构思考

改造过程中把记忆拆成三层：

1. **短期工作单记忆（Redis）**：当前会话上下文，随对话轮次更新。
2. **中期商户画像（MySQL/Postgres）**：商户长期属性、历史工单摘要。
3. **长期诊断模式库（向量库）**：相似历史案例、根因模式。

与 Aligo 旅行情景记忆的区别：

- 旅行情景更关注"当前出差人偏好 + 差旅政策"。
- 工单诊断更关注"商户实体 + 故障模式 + 责任归属"。

实现上采用**最小修改**：保留原有短期记忆参数，新增 `merchant_profile` 和 `diagnosis_patterns` 两层，扩展 `MemoryManager` 而不重写。

## 五、离线评测体系

建立 44 条评测数据，覆盖：

- 意图识别
- 根因判断
- 责任归属

通过 `scripts/run_evaluation.py` 批量运行，输出 `Pass@1`、命中率等指标。评测不是为了刷分，而是为了：

1. 建立能力基线，后续改造有据可依。
2. 快速发现回归，避免改 A 坏 B。

第一批基线：`Pass@1 77.27%`。后续可通过增强实体提取、扩充知识库来提升。

## 六、通用经验

### 6.1 先让链路能跑，再优化细节

Batch 1 最开始是"骨架回归"：IntentionAgent -> OrchestrationAgent -> LazyAgentRegistry -> 专业 Agent 能跑通，再逐步把 loop 控制、trace、响应构造收口。

如果一开始就追求完美架构，很容易陷入大规模重构，风险不可控。

### 6.2 mock 不是坏事，关键是接口稳定

Batch 2 补齐 30 个原子 Skill 时，底层数据先用 mock。但接口（输入/输出字段、状态枚举）先定下来，后续换真实数据源时上层不用改。

### 6.3 测试要覆盖"不可用"场景

RAG 依赖很容易因为环境、模型缺失、Milvus 损坏而失败。测试里专门加了：

- RAG Agent 不可用时 IntentionAgent 仍能用规则识别。
- RAG Agent 不可用时 ResolutionAgent 仍能做归属判定。
- 真实依赖未安装时跳过向量库测试。

这比只测"Happy Path"有价值得多。

### 6.4 动态导入要谨慎处理 sys.path

`.claude/skills/ask-question/script/agent.py` 是通过 `importlib.util` 动态加载的，模块内部会 `import utils.xxx`、`from config import ...`。必须在加载前确保项目根目录在 `sys.path` 中：

```python
project_root = str(Path(__file__).parent.parent.absolute())
if project_root not in sys.path:
    sys.path.insert(0, project_root)
```

否则在不同目录下运行脚本时会报 `ModuleNotFoundError`。

## 七、后续可继续优化项

1. **RAG 多 collection 拆分**：当前 `SearchHistoryTicket` 和 `SearchPolicyFAQ` 复用同一个 collection，后续可按文档类型拆分。
2. **OCR 补全架构图**：PDF 图多文本少时，引入 PaddleOCR / tesseract 生成图片描述 chunk，这是提升 RAG 效果最直接的途径。
3. **多 PDF 批量导入**：目前一次只处理一个文件，可扩展为 `python scripts/init_diagnosis_kb.py --dir data/documents/`。
4. **动态阈值调优**：当前 `min_similarity_threshold=0.55` 是经验值，后续可基于评测集自动搜索最佳阈值。
5. **前端诊断追踪面板**：Batch 4 仍是空白，React + SSE 实时展示 Agent 协作链。
