## 一、Skill 设计哲学
### 核心原则：原子化 + 可组合 + 可观测
```plain
原子化：每个 Skill 只做一件事，输入输出明确
可组合：通过 OrchestrationAgent 编排原子 Skill 完成复杂诊断
可观测：每个 Skill 执行过程可追踪、可解释
```

## 二、原子化 Skill 清单（按数据源+业务实体拆分）

| `GetMerchantContract` | `merchant_id` | 合同类型、分润比例、有效期起止、签署状态、续签记录 | 合同档案表 |
| `GetMerchantOrgTree` | `merchant_id` | 父商户ID、子商户列表、组织层级路径 | 组织架构表 |
| `GetMerchantPermission` | `merchant_id`, `employee_id` | 角色列表、权限点集合、租户隔离标识 | 权限配置表 |
| `GetMerchantOnboarding` | `merchant_id` | 入驻申请状态、审核记录、资质核验结果、入驻完成时间 | 入驻申请表 |
| `GetMerchantBlacklist` | `merchant_id` | 是否风控限制、限制原因、限制类型、解限条件 | 风控记录表 |

## 三、Skill 组合编排示例（诊断路径映射）
### 场景1：订单支付成功但服务未生效
```plain
用户输入: "订单ORD007付了198元但柜机还是提示未开通"

OrchestrationAgent 调度决策:
┌─────────────────────────────────────────────────────┐
│ Stage 1: 并行获取基础信息（3个原子Skill并行）      │
├─────────────────────────────────────────────────────┤
│ GetOrderDetail → 订单状态=PAID, 支付时间=14:32    │
│ GetOrderTimeline → 支付成功回调未触发              │
│ GetAssetAllocation → 用户侧权益未激活              │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ Stage 2: 条件触发（根据Stage1结果按需加载）        │
├─────────────────────────────────────────────────────┤
│ TraceRequestLog → 支付回调日志: timeout 505        │
│ GetMerchantCoopStatus → 商户状态正常               │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ Stage 3: 交叉验证                                  │
├─────────────────────────────────────────────────────┤
│ ReconstructTimeline → 14:32支付完成，14:33回调超时 │
│ ValidateFrontendState → 前端显示"待激活"           │
│ SearchHistoryTicket → 相似工单20260515-回调超时转后端│
└─────────────────────────────────────────────────────┘
                          ↓
最终判定: 后端支付回调超时 → 转后端团队处理
```

### 场景2：商户无法分配免时长给员工
```plain
用户输入: "商户M10001有500天免时长，但分配时提示余额不足"

OrchestrationAgent 调度决策:
┌─────────────────────────────────────────────────────┐
│ Stage 1: 并行获取资产状态                          │
├─────────────────────────────────────────────────────┤
│ GetAssetPool → 总500天, 已分配480天, 剩余20天    │
│ GetAssetAllocation → 查询已分配明细               │
│ GetUserBinding → 目标用户已绑定其他商户            │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ Stage 2: 深入排查                                  │
├─────────────────────────────────────────────────────┤
│ GetProtectionPeriod → 该用户保护期至2026-08-15    │
│ GetMerchantPermission → 操作者无跨商户分配权限     │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ Stage 3: 根因分析                                  │
├─────────────────────────────────────────────────────┤
│ 原因1: 商户剩余额度仅20天 < 目标分配100天 → 额度不足│
│ 原因2: 目标用户在另一商户保护期内 → 归属冲突       │
│ 原因3: 操作者无跨商户权限 → 权限不足               │
└─────────────────────────────────────────────────────┘
                          ↓
最终判定: 三重限制叠加 → 建议引导商户完成:
        1. 回收未使用额度 / 采购新套餐
        2. 等待保护期结束或联系业务解绑
        3. 申请跨商户分配权限
```

### 场景3：结算金额与合同不符
```plain
用户输入: "本月结算少了3000块，合同签的是联营50%分润"

OrchestrationAgent 调度决策:
┌─────────────────────────────────────────────────────┐
│ Stage 1: 并行获取合同与账单                        │
├─────────────────────────────────────────────────────┤
│ GetMerchantContract → 联营模式, 分润比例=50%      │
│ GetBillDetail → 本月账单总额6000, 实结3000        │
│ GetSettlementRule → 商户标签=直营(60%分润)        │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ Stage 2: 一致性校验                                │
├─────────────────────────────────────────────────────┤
│ GetMerchantProfile → 商户类型=KA, 标签=直营       │
│ GetBillCalculation → 计算逻辑: 6000 × 60% = 3600 │
│ 差异: 合同50%(3000) vs 实际60%(3600) 方向反了     │
└─────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────┐
│ Stage 3: 查找根因                                  │
├─────────────────────────────────────────────────────┤
│ GetSettlementTimeline → 结算标签在5月被数据脚本刷  │
│ SearchHistoryTicket → 20260515批次数据更正事件     │
│ ReconstructTimeline → 复核时误将联营改为直营       │
└─────────────────────────────────────────────────────┘
                          ↓
最终判定: 数据标签错误 → 转数据团队修正标签 + 补发结算差额
```

### （三）评分维度
#### 定量指标
| 指标 | 计算方式 | 目标值 |
| --- | --- | --- |
| **意图识别准确率** | 正确识别投诉所属域 / 总工单数 | ≥ 93% |
| **实体召回率** | 正确抽取实体数 / 应有实体数 | ≥ 90% |
| **原子Skill调用准确率** | 正确调用的Skill / 应调用的Skill | ≥ 92% |
| **RAG命中率** | 召回有效文档 / 需要RAG的Case | ≥ 95% |
| **3轮闭环成功率** | 3轮内完成诊断 / 总Case数 | ≥ 87% |
| **归属判定准确率** | 正确判定根因归属 / 完成诊断 | ≥ 93% |


#### 定性指标
| 指标 | 描述 | 评估方式 |
| --- | --- | --- |
| **解释性** | 诊断过程是否可追溯、可理解 | 人工抽检 |
| **原子Skill执行效率** | 并行调度是否充分利用 | 耗时监控 |
| **降级表现** | 单Skill失败时是否优雅降级 | 故障注入测试 |

## 五、Skill 调度策略与降级方案
### 调度策略矩阵
| 场景类型 | 调度策略 | 超时设置 |
| --- | --- | --- |
| 基础信息查询 | 全部并行 | 3s |
| 深度日志追踪 | 条件触发（按需加载） | 5s |
| 跨域交叉验证 | 依赖前置结果 | 2s |
| RAG检索 | 与业务Skill并行 | 3s |


### 降级策略
| 异常类型 | 降级行为 |
| --- | --- |
| 单原子Skill超时（>3s） | 返回部分结果 + 标注"该维度查询超时" |
| 单原子Skill报错 | 记录错误但继续执行其他Skill |
| RAG服务不可用 | 跳过知识库检索，仅执行业务Skill |
| 日志平台不可用 | 仅依赖业务数据库查询 |

## 六、总结
本设计将Skill细化为 **25个原子Skill** + **5个通用辅助Skill**，覆盖商家管理、商家经营、资金结算三大业务域，通过OrchestrationAgent按需编排组合，实现：

> **30分钟人工排查 → 15秒自动化诊断，7×24小时无人值守，93%+归属准确率，可解释可追溯。**
>

核心理念：**原子化保证可测性和复用性，编排保证复杂场景覆盖，降级保证高可用。**
