## 0. 摘要（TL;DR）

- 当前系统是「静态策略矩阵 + 黑板存事实」的中间态，能稳定跑通但尚未达到「假设驱动的多 Agent 协作」。
- 本次收口不推倒重来，而是把已有的两块积木（`DiagnosisState` 黑板、`StrategyMatrix` 调度）**增量升级**：黑板从「存结论」升级为「存假设」，调度从「静态排期」升级为「假设路由 + 静态兜底」。
- 核心边界一句话：**Scheduler 决定「谁来做」（Agent 级路由），Agent 决定「做什么」（工具/字段级决策）**。二者不冲突，这是 Multi-Agent 成立的前提。
- **假设类型体系**：`type` 是「证据维度」闭集（6 个枚举），`detail` 是「具体根因」开放文本；路由映射是「维度 → 候选 Agent（一对多）」，避免沦为 scenario 换皮。
- 冲突面评估结论：**低冲突、增量、可回滚**。唯一中风险点是「解耦 Agent 硬引用 × Role-aware 事实域裁剪」，需单独验收。

## 1. 背景与动因

### 1.1 前情：已经迭代过 7 版架构

`改造TODO.md` 的「改造偏移记录」已沉淀偏移 1~7，包含：

- 偏移 1：确定性调度显性化（OrchestrationAgent 去壳 → `Scheduler`）
- 偏移 6：Role-aware Context（按角色裁剪上下文）
- 偏移 7：协作证据链 + 分层自主性边界（`allowed_tools` 白名单 + `enable_llm_autonomy` 开关 + `_call_llm` 接入点）

偏移 7 落地了 CodeAgent 的「探索型 LLM 动态决策」（`_is_ambiguous → _llm_deep_dive → _parse_decision`）。

### 1.2 本次动因

CodeAgent 引入 LLM 决策后，引出三个更深层的架构问题：

1. **策略矩阵要不要适配 LLM 决策？** → 结论：不需要，因为调度层管「调哪个 Agent」，LLM 决策发生在 Agent 内部，二者分层。
2. **黑板存的是「结论」而非「假设」** → Scheduler 没有「待验证项」可扫，无法做假设驱动路由。
3. **Agent 之间通过 `previous_results` 硬编码互相引用** → 违反「零耦合」，新加 Agent 要改多处。

这三个问题不解决，「Multi-Agent」这个词就站不住——CodeAgent 只是跑在 workflow 里的一个确定性组件，而非真正基于运行时证据自主决策的 Agent。

### 1.3 收口目标

一次性定义清楚「Scheduler 管什么、Agent 管什么、黑板承载什么」，把后续工作收敛成可独立验证的阶段，避免继续横跳。

## 2. 目标架构定位

### 2.1 三档自治梯度

| Agent | 自治类型 | LLM 角色 | 自由度边界 |
|---|---|---|---|
| OperationAgent | 流程型（Flow-based） | 不引入 LLM，保持确定性 | 固定流程，可复现性最强 |
| DataAgent | **受控解读型**（Constrained Interpreter） | LLM 只做**结果归因 + 冲突检测**，不做工具选择 | 无工具选择权、无流程跳转权 |
| CodeAgent | 探索型（ReAct-lite） | LLM 决定**深挖哪条链路** | 有单步工具选择权，受白名单 + `max_steps` 护栏 |

三者共享同一套安全护栏：

- `enable_llm_autonomy` 开关短路（默认关）
- `self.model is None` 降级到确定性规则
- `allowed_tools` 白名单物理隔离（`_execute_tool` 拦截越界）
- `max_steps` 步数上限

**CodeAgent 与 DataAgent 的边界（关键）**：区别不在「谁调 LLM」，而在「LLM 有没有工具选择权」。

- CodeAgent：LLM 输出 `decision` 决定**要不要继续查、查哪条链路**（有工具选择权）。
- DataAgent：规则先跑完固定查询，LLM 只对**已查到的结构化结果**做归因/冲突判别（无工具选择权）。

一句话：CodeAgent 的 LLM 是「决策器」，DataAgent 的 LLM 是「解读器」。

### 2.2 核心边界：路由 ≠ 查什么

| 决策层 | 谁 | 回答的问题 | 粒度 |
|---|---|---|---|
| 路由（Routing） | Scheduler | 「这个假设该交给**哪个专业域**」 | Agent 级 |
| 排查（Investigation） | Agent | 「具体查**哪个接口/字段/配置**」 | 工具/字段级 |

- Scheduler 看到黑板上的「假设：payment_callback 未调用」，判断这是数据链路的事，派给 DataAgent —— 这是**路由**。
- DataAgent 具体查哪条回调日志、怎么比对状态码 —— 这是**排查**，Scheduler 不碰。

「Scheduler 根据假设类型决定调度哪个 Agent」**不等于**「Scheduler 决定下一步查什么」。前者是 Agent 级路由，后者是工具级决策。这个边界守住，CodeAgent 就不会退化成 workflow runner。

### 2.3 假设类型体系（核心设计）

**原则：`type` 是「证据维度」闭集，不是「具体根因」开放集，也不是「嫌疑 Agent」映射。**

假设的数据结构：

```python
{
    "type": "api_trace",                 # 证据维度（闭集枚举）
    "detail": "payment_callback 未调用",  # 具体假设内容（开放文本）
    "status": "pending",                 # pending / verified / refuted
    "proposed_by": "CodeAgent",          # 提出者
    "evidence": ["..."]                  # 支撑证据
}
```

证据维度闭集（跨场景复用，6 个）：

| type | 语义 | 需要的证据 |
|---|---|---|
| `api_trace` | 查接口/链路日志 | 回调、超时、错误码 |
| `db_state` | 查数据库/跨表状态 | 快照、状态不一致 |
| `config_state` | 查配置/开关 | 权限点、开关、额度规则 |
| `biz_flow` | 查业务流程/操作轨迹 | 时间线、操作步骤 |
| `policy` | 查规则/政策/契约 | 合同、结算规则、标签 |
| `cross_verify` | 多域交叉验证 | 多 Agent 证据互证 |

路由映射（**维度 → 候选 Agent，一对多**，体现协作而非分工）：

```python
HYPOTHESIS_ROUTING = {
    "api_trace":    ["CodeAgent"],
    "db_state":     ["DataAgent"],
    "config_state": ["CodeAgent", "OperationAgent"],
    "biz_flow":     ["OperationAgent"],
    "policy":       ["OperationAgent", "DataAgent"],
    "cross_verify": ["CodeAgent", "DataAgent"],
}
```

**为什么这样设计能同时避开两个坑**：

| 方案 | type 语义 | 问题 |
|---|---|---|
| 粗粒度映射 Agent | `code_anomaly → CodeAgent` | scenario 换皮 |
| 细粒度映射 Agent | `payment_callback_missing → CodeAgent` | 开放集爆炸、维护成本高 |
| **证据维度映射（采纳）** | `api_trace → 能查链路的 Agent` | type 闭集、跨场景复用、一对多协作 |

关键点：`type` 描述的是「**需要验证什么证据维度**」，而非「谁有嫌疑」或「具体是什么根因」。同一个 `type="api_trace"` 的假设，`detail` 可以是「回调未调用」「回调超时」「错误码异常」——type 不变，detail 自由。这样 type 体系既稳定（闭集）又保留表达力（detail 开放）。

### 2.4 黑板 + Scheduler 协同四步

1. 专业 Agent 执行排查任务，把 **Hypothesis（假设）** + 证据写入黑板。
2. Scheduler 扫描黑板中的待验证项，按**证据维度 → 候选 Agent** 决定下一轮调度谁。
3. 被调度 Agent 验证假设，把结果（verified/refuted）写回黑板。
4. 证据累积到阈值（≤3 轮），ResolutionAgent 综合判定。

**ResolutionAgent 定位（诚实降级）**：当前阶段它是「**规则归因 + 结构化汇总**」——把多 Agent 的 `path_verdict`/`inconsistency_found` 按规则归因到归属方，**不是**「LLM 仲裁冲突」。真正的「多 Agent 结论矛盾时的仲裁」是阶段 4 之后的扩展点，不提前承诺实现，避免面试被追问「怎么解决 Agent 冲突」时接不住。

核心优势：**Agent 零耦合**。CodeAgent 不需要知道 DataAgent 存在；新加 Agent 只需在 `HYPOTHESIS_ROUTING` 里加一条映射，已有 Agent 不受影响。

### 2.5 闭环验证：假设状态机（通信 + verification 闭环）

当前框架的通信与 verification **物理上能跑通，但语义上断了两处**，必须靠假设状态机补齐：

- **断点 1**：Round 3 的 `_follow_up` 是空转（`tools_called=[]`，只复读前序结论），Agent 在交叉验证轮不产生新判断。
- **断点 2**：ResolutionAgent 读的是 `path_verdict` **字符串**做 `if-else` 归因，不是「验证假设 true/false」。

补齐后的闭环链路：

```
CodeAgent 写 hypothesis{status: pending}
        ↓
Scheduler 路由到能验证该 type 的 Agent（注入 pending_hypotheses）
        ↓
被路由 Agent 用 allowed_tools 查证 → 写回 status: verified / refuted
        ↓
ResolutionAgent 读 hypothesis.status 做归因（不再只读 path_verdict 字符串）
```

**关键对称：路由映射 = 验证能力映射**。路由到某个 Agent，恰恰因为它有能力验证这个 type：

| 假设 type | 路由到的 Agent | 该 Agent 用来验证的工具 |
|---|---|---|
| `db_state` | DataAgent | `check_data` / `query_settlement` |
| `api_trace` / `config_state` | CodeAgent | `trace_api` / `check_config` |
| `biz_flow` / `policy` | OperationAgent | `query_order` / `search_policy_faq` |

「假设被路由」即「假设被指派了验证者」，验证动作落在被路由 Agent 的 follow_up 里，闭环自然合上。这一对称也让「零耦合」成立：Agent 不需要知道别的 Agent，只需要响应「验证某个 type 的假设」这个通用任务。

```python

class ResolutionAgent(BaseResolutionAgent):
```

因此主服务通过 [LazyAgentRegistry](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/lazy_agent_registry.py) 懒加载的 Agent，**最终执行的仍是 `agents/*.py` 的逻辑**。改 `agents/` 目录一定生效，不存在「改错文件」风险。

### 3.2 Scheduler 职责对照

| 目标职责 | 当前实现 | 状态 |

| schema | [AgentResult](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/context/diagnosis_state.py#L19-L55)（pydantic） | ✅ 有 |

### 3.3 三个关键差距

**差距 1：黑板缺「假设」语义层**

[DiagnosisState.facts](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/context/diagnosis_state.py#L58-L67) 存的是「事实 + 结论」，不是「假设 + 待验证」：

- 现在：`order_id` / `code_path_detail` / `path_verdict` / `inconsistency_found`
- 需要：`hypothesis`（含 type、detail、status、proposed_by、evidence）

**差距 2：Scheduler 是静态矩阵，不扫描黑板**

[Scheduler._build_schedule](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/scheduler.py#L166-L179) 只读 `scenario + round_num`，用 [StrategyMatrix](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/scheduling/strategy_matrix.py#L116-L280) 的静态表 `scenario × round → 固定 Agent 列表` 输出调度计划。它不读黑板上的假设，无法「根据假设类型动态路由」。

**差距 3：Agent 之间硬耦合**

[CodeAgent._follow_up](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/code_agent.py#L283-L300) 与 [OperationAgent._follow_up](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/operation_agent.py#L151-L166) 里硬编码了其他 Agent 名：

```python
data_result = self._find_previous_result(previous_results, "DataAgent")  # 硬编码
code_result = self._find_previous_result(previous_results, "CodeAgent")
```

这违反零耦合：Agent 精确知道「谁」产出了「什么」，新加 Agent 时这些硬编码都要跟着改。

**差距 4：Round 3 交叉验证是空转**

[DataAgent._follow_up](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/data_agent.py#L162-L175) 与 [CodeAgent._follow_up](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/code_agent.py#L282-L299) 在 Round 3 里 `tools_called=[]`，只回「数据侧复核后确认前序异常结论」这类固定字符串，**不查任何工具、不产生新判断**。真正判断全压在 ResolutionAgent 的规则归因上，所谓「交叉验证」是名义上的。这是「假设状态机」要补齐的核心缺口。

## 4. 冲突面评估

### 4.1 总体结论

**低冲突、增量、可回滚。** 本次演进不推翻现有主链路，每一阶段都能独立验收、不破坏现有 115+ 回归测试与离线评测 5 项指标。

### 4.2 分级评估

| 阶段 | 冲突等级 | 原因 | 回滚成本 |
|---|---|---|---|
| 阶段1 黑板补 hypothesis 字段 | 🟢 低 | `AgentResult` 用 `extra="allow"` + `exclude_none=True`，加字段无副作用 | 删字段即可 |
| 阶段2 假设路由规则 | 🟢 低 | 静态矩阵全程兜底，无假设时行为与现在一致 | 关规则开关即可 |
| 阶段3 解耦 Agent 硬引用 | 🟡 中 | 需与 Role-aware 事实域裁剪对齐 | 逐文件 git 回滚 |
| 阶段4 Scheduler 收口治理 | 🟡 中 | 分散改 timeout/budget/权限，但彼此独立 | 分项回滚 |

### 4.3 唯一高风险点（需重点设计）

阶段 3 的「解耦 Agent 硬引用」与 [Role-aware Context 的事实域裁剪](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/scheduler.py#L56-L82) 存在交互风险：

- 当前 `_AGENT_CONTEXT_PROFILE` 里，CodeAgent 的 `fact_domains` 是 `{order, settlement}`，OperationAgent 是 `{order, merchant, knowledge}`。
- 如果 Agent 改成「只读 `collected_data.facts` 黑板」，而它要读的字段（如别的 Agent 的 `path_verdict`）不在自己的事实域内，就会被 Role-aware 裁剪掉，导致读不到。

**最小落点**：把 `hypothesis`、`findings`、`inconsistency_found`、`final_verdict` 这类「协作字段」纳入 `_ENTITY_FACT_KEYS` 式的**常驻白名单**，不参与 `fact_domains` 裁剪，对所有 Agent 全局可读。

**目标态（阶段 4 或后续，避免过度抽象）**：显式拆成双层黑板——

```python
class Blackboard:
    shared: Dict      # hypothesis / findings / final_verdict —— 全局可读
    role_facts: Dict  # 按 Agent 类型裁剪的领域事实
```

先用「常驻白名单」最小实现，跑通后再决定是否抽 `Blackboard` 双层结构，避免阶段 3 一次引入过多抽象。

### 4.4 改造爆炸半径（五子系统影响范围）

**结论：只碰「调度」和「上下文管理」两层，skills 和记忆零改动。**

| 子系统 | 是否伴随改造 | 程度 | 依据 |
|---|---|---|---|
| 架构（黑板 + Scheduler） | ✅ 必须 | 核心 | 它本身就是改造对象 |
| 子任务调度 | ✅ 必须 | 中 | 假设路由 + 治理收口落在这里 |
| 上下文管理 | ✅ 必须 | 轻 | 协作字段白名单 + 假设注入落在这里 |
| skills | ❌ 不动 | 仅消费 | 验证动作「调用」已有 skill/tool，不改 skill 本身 |
| 记忆 | ❌ 不动 | 无 | 假设是单次诊断内状态，不进长期记忆 |

**① 子任务调度（必须动，但分清两层）**

| 层 | 落点 | 改什么 |
|---|---|---|
| Agent 级调度 | `StrategyMatrix` | 阶段 2 加 `HypothesisRoutingRule`（merge 去重） |
| Agent 内部 skill 编排 | 各 Agent 的 `_follow_up` | 阶段 3 从「空转」改成「调 skill 验证假设」 |

注意：第二层改的是「调哪些 skill 的时序」，不是 skill 本身。

**② 上下文管理（必须轻动）**

落点在 [scheduler.py 的 Role-aware 裁剪](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/agents/scheduler.py#L52-L235)：

- `_ENTITY_FACT_KEYS` 加入 `hypothesis` / `findings` 等协作字段（常驻白名单）。
- `pending_hypotheses` 注入 context 时不能被 `fact_domains` 裁掉。

改动即「加几个字段到白名单 + 注入一个协作字段」，**不重构裁剪机制**。

**③ skills（不动，只被消费）**

假设验证动作是「Agent 在 follow_up 调用 `allowed_tools` 里已有的工具查证」，例如 DataAgent 验证 `db_state` 假设时调 `check_data`。这些 skill/tool 已存在，不需要新增或修改。`allowed_tools` 白名单也不需要扩——验证动作用的工具，正是路由映射里「该 Agent 能验证该 type」的那批工具，白名单已覆盖。

**④ 记忆（不动）**

关键边界：**假设 ≠ 记忆**，生命周期不同。

- 假设（hypothesis）是**单次诊断内的黑板状态**，靠 [state.facts 跨轮合并](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/services/diagnosis_service.py#L498-L515) 存活，随诊断结束销毁。
- 记忆（MemoryManager）是**跨会话持久化**，介入点只有三处：记录用户消息、注入意图上下文、诊断结束 `record_diagnosis`。

假设不进长期记忆，记忆系统一行不改。若未来要「把验证过的假设沉淀成诊断模式库」，那是 RAG/`pattern_store` 的事，超出本次范围。

## 5. 演进方案（4 阶段）

### 阶段 1｜黑板补「假设」语义层（低风险）

- 给 [AgentResult](file:///Users/yuchen/Learning-library/demo/小哈工单智能诊断助手agent/context/diagnosis_state.py#L19-L55) 加可选字段 `hypothesis`（结构化：type / detail / status / proposed_by / evidence）。
- CodeAgent 的 `_llm_deep_dive` 产出 `llm_decision.root_cause` 时，同步写一个 `hypothesis: {type: "api_trace", detail: <root_cause>, status: "pending"}`。
- `EXCLUDED_KEYS` 不排除 `hypothesis`，让它自然沉淀进 `facts`，但 ResolutionAgent 暂不消费它（先写不读，零风险）。
- **验收**：现有回归 + 评测全绿；`facts` 中能看到 `hypothesis` 字段，且 `type` 命中 6 个闭集维度之一。

### 阶段 2｜Scheduler 加「假设路由规则」（低风险）

- 在 `StrategyMatrix` 新增一条 `HypothesisRoutingRule`：
  - 扫描 `collected_data.facts` 里的 pending hypothesis；
  - 按 `HYPOTHESIS_ROUTING[type]` 得到候选 Agent 列表；
  - **merge（追加去重）**：把候选 Agent 追加到静态矩阵基线计划，同一 Agent 若已在基线中则**去重**（保留基线 reason，附加假设 detail 到 `expected_output`），不 override 基线；
  - **注入验证任务**：把 pending hypothesis 作为 `pending_hypotheses` 协作字段注入被路由 Agent 的 context（进常驻白名单，不被 Role-aware 裁剪）。
- **优先级澄清（merge 而非 override）**：

```python
def build_schedule(scenario, round_num, blackboard):
    base = strategy_matrix[scenario][round_num]      # 1. 静态基线
    routed = route_hypotheses(blackboard.pending)     # 2. 假设路由
    return merge_dedupe(base, routed)                 # 3. 追加 + 按 agent_name 去重，基线优先
```

  - 不 override 的理由：静态矩阵保证高频场景的确定性覆盖不丢失，override 会破坏现有评测的确定性兼容。
- 配置入口放 `SchedulingSettings`，加 `enable_hypothesis_routing` 开关（默认关，可独立验证）。
- **验收**：关开关 → 行为与现在一致；开开关 → 有假设时追加路由 Agent（去重），无假设时仍走静态矩阵。

### 阶段 3｜假设验证 + 解耦 Agent（中风险，单独验收）

- **follow_up 从空转变验证**：被路由 Agent 的 `_follow_up` 不再空转，而是读 `pending_hypotheses`，用自己 `allowed_tools` 里匹配的工具针对性查证，写回 `hypothesis.status = verified / refuted` + 验证证据（`tools_called` 不再是空列表）。
- 把 `_find_previous_result(..., "DataAgent")` 等硬引用，改为从 `collected_data.facts` 读黑板。
- 处理 4.3 的裁剪交互风险：协作字段（`hypothesis`/`findings`/`inconsistency_found`）纳入常驻白名单。
- 新增 Agent 时，只需在 `HYPOTHESIS_ROUTING` 加一条映射，不改已有 Agent 代码。
- **验收**：① 新增一个「占位 Agent」验证零耦合（不触碰 CodeAgent/OperationAgent/DataAgent 源码即能接入调度）；② 一条 pending hypothesis 被路由 Agent 验证后，`status` 从 `pending` 变为 `verified` 或 `refuted` 且带验证证据。

### 阶段 4｜Scheduler 收口治理（中风险，可延后）

- `budget`：让 `max_steps` 真正计数（在 `_execute_tool` 调用链上累加，超限截断）。
- `timeout`：Scheduler 层加 per-agent timeout，超时标记 `degraded`。
- 权限：把「哪些 Agent 在哪些轮次可被调度」的治理显式收口到 Scheduler。
- ResolutionAgent「冲突仲裁」作为本阶段之后的**扩展点**（不承诺实现，标注即可）。
- **验收**：Scheduler 具备完整的「最大轮数 / 权限 / timeout / budget / schema」五项治理能力，Agent 只保留专业领域决策。

1. **扩 mock 数据**：`api_logs.json` 已加 ORD-9101/9102（多订单多异常）；再为 asset/settlement 补「双因歧义」快照。

4. **双态回归**：
   - `enable_llm_autonomy=false` → 动态 case 主因关键词 miss → 失败（证明 LLM 非摆设）；
   - `enable_llm_autonomy=true` → 主因关键词命中 → 通过。

## 7. 实施顺序与冻结点

建议顺序（投入产出比）：

1. **阶段 1 + 阶段 2**（打通「LLM 决策 → 假设 → 跨 Agent 路由」闭环，风险低、价值最高）
2. **评测闭环**（阶段 1/2 之后立即验证，形成「关 LLM 过不了、开 LLM 能过」的证据）
3. **阶段 3**（解耦，独立验收，是「零耦合」叙事的关键）
4. **阶段 4**（治理收口，可延后到面试前统一补）

**冻结点声明**：阶段 1~4 完成后，本项目的调度架构定位即固定为「确定性 Scheduler 兜底 + 黑板假设驱动路由 + Agent 分层自治」，不再引入「全自主 LLM 协商」（过度设计）。完整 ReAct/Plan-and-Execute 自由循环仍以「真实 LLM API + 真实数据」为前置，不提前启用。
