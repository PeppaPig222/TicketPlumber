# 小哈工单智能诊断助手 — 开发手记

> 记录项目改造过程中有价值的设计决策、迭代优化思路，以及踩过的坑和解决方案。
> 面向对象：后续维护者、面试复盘、自己回头查。

---

## 一、项目改造背景

项目最初是打算设计为一个"受控多 Agent"工单诊断 demo，准确度高但架构偏 workflow runner。改造目标是在保留诊断能力的前提下，逐步回归 通用多 Agent / Skill 插件化主链路：

```
CLI/API -> IntentionAgent -> OrchestrationAgent -> LazyAgentRegistry -> 专业 Agent -> Skill
```

改造遵循两个原则：

1. **最小改动**：尽量在原有结构上扩展，不推倒重来。
2. **可验证**：每批改动都补测试、跑回归，保证 3 个高频场景闭环不降级。

## 二、Batch 1：多 Agent 角色层落地

### 2.1 专业 Agent 插件化

把 `CodeAgent / OperationAgent / DataAgent / ResolutionAgent` 从 `agents/` 硬编码实现迁移到 `.claude/skills/` 下的独立 skill 目录，每个目录包含：

- `SKILL.md`：职责说明
- `script/agent.py`：插件入口，从 `agents.xxx_agent` 导入真实实现

**为什么这么做**：

- 让 `LazyAgentRegistry` 成为主链路的一部分，符合 Aligo "Skill 即能力单元"的设计。
- 后续新增 Agent 只需新建 skill 目录，不用改 `DiagnosisService`。

### 2.2 遇到的坑：PascalCase 调度名 vs kebab-case 目录名

`OrchestrationAgent` 里调度用的是 `"CodeAgent"`，但 skill 目录名是 `"code-agent"`，导致 `LazyAgentRegistry.__getitem__` 找不到 Agent。

**解决方案**：在 `LazyAgentRegistry` 中增加 `_agent_alias_mapping`：

```python
self._agent_alias_mapping = {
    "CodeAgent": "code-agent",
    "OperationAgent": "operation-agent",
    "DataAgent": "data-agent",
    "ResolutionAgent": "resolution-agent",
}
```

并调整 `_resolve_agent_name` 优先级：skill 目录名 > 专业 Agent 别名 > legacy mapping > custom_factories。

### 2.3 依赖注入：agent_kwargs

`LazyAgentRegistry` 支持通过 `agent_kwargs` 给 skill Agent 注入依赖（如 `skill_registry`、`rag_agent`）。

```python
agent_registry = LazyAgentRegistry(
    model=None,
    cache={},
    memory_manager=memory_manager,
    agent_kwargs={
        "skill_registry": self.skill_registry,
        "rag_agent": self.rag_agent,
    },
)
```

关键点：`_load_from_skill` 里用 `inspect.signature(agent_class.__init__)` 判断是否接受某个 kwarg，只注入匹配的参数，避免不同 Agent 构造函数不一致导致报错。

## 三、Batch 5：正式 RAG 知识库

### 3.1 设计目标

把 `knowledge_base.json` 的 keyword 检索升级为基于向量库的正式 RAG，并且接入诊断主链路：

- `IntentionAgent`：规则识别失败时，用 RAG fallback 推断 scenario。
- `ResolutionAgent`：归属判定阶段，用 RAG 补充证据链。
- `DiagnosisService`：统一管理 `RAGKnowledgeAgent` 实例。

### 3.2 为什么 RAG Agent 不直接改 `tool_registry.search_kb`

考虑过把 `tool_registry` 里的 `search_kb` 直接换成向量检索，但最终没这么做：

- `tool_registry` 定位是轻量工具注册中心，底层 mock 数据源。
- RAG 依赖 pymilvus + sentence-transformers，初始化较重，失败时不应阻断 tool_registry 其他工具。
- 由 `DiagnosisService` 统一创建并注入给需要的 Agent，更符合"外部能力可插拔"的设计。

结果是：RAG 可用时用 RAG，RAG 不可用时规则链路仍然完整运行。

### 3.3 PDF 复杂架构图的处理

用户只有一份商户 PDF，且**几乎全是架构图**，`pdfplumber.extract_text()` 基本提取不到成段文字。

如果简单处理，每个图页只生成一句 `"[架构图：第 X 页，无法提取]"`，向量库里就是一堆没有信息量的 chunk，检索时根本匹配不到。

**优化策略**：

1. **多维度检测图页**：字数少、检测到 `page.images`、绘制元素（线/矩形/曲线）多，都视为图页。
2. **提取图上文字碎片**：用 `extract_words()` 捞出模块名、标签、箭头文字，按 y 坐标分行整理。
3. **上下文关联**：把图页和前后相邻页的标题/关键词拼进占位 chunk，提升可检索性。
4. **预留 OCR 扩展点**：chunk 里提示"建议后续通过 OCR 或人工标注补充"，当前不引入新依赖。

占位 chunk 示例：

```
[架构图/流程图：第 12 页]
来源文档：merchant_architecture.pdf
图上可识别的系统组件/关键词：结算中心, 分润比例, 商户标签, 结算规则
图上文字碎片：
  - 结算中心 -> 商户标签 -> 分润比例
相邻页上下文：
  - 第11页：订单支付与退款流程；关键词：支付网关, 退款回调, 订单状态
  - 第13页：资产分配与保护期；关键词：资产池, 保护期, 跨商户分配
说明：本页主要内容来自复杂架构图/流程图，文本无法完整自动提取。建议后续通过 OCR 或人工标注补充完整流程说明。
```

实际效果：初始化后 37 个 chunks 全是架构图占位，但测试检索仍能命中相关页码。

### 3.4 遇到的坑

#### 坑 1：Milvus Lite URI 格式

`RAGKnowledgeAgent` 原来用：

```python
self.milvus_client = MilvusClient(uri=f"file:{milvus_db_path}")
```

在不同环境（base conda / .venv）下表现不一致：

- 有时报错 `Open local milvus failed, dir: ... not exists`
- 有时报错 `database 'private' does not exist`

**原因**：`pymilvus 2.6.9` 会把 `file:/path` 解析出 `db_name='private'`（路径第一段）。

**解决方案**：去掉 `file:` 前缀，并显式指定 `db_name="default"`：

```python
self.milvus_client = MilvusClient(uri=milvus_db_path, db_name="default")
```

重连逻辑也要同步改：

```python
self.milvus_client = MilvusClient(self._milvus_db_path, db_name="default")
```

#### 坑 2：`milvus_lite.db` 变成了目录

删除重建时，如果 `data/rag_knowledge/milvus_lite.db` 已经是一个目录，再运行初始化会直接失败。

**原因**：Milvus Lite 在当前版本下会把 `.db` 路径作为一个数据目录使用。如果之前旧代码用 `file:` 前缀写坏了，或者手动创建过目录，就会冲突。

**解决方案**：

```bash
rm -rf data/rag_knowledge/milvus_lite.db
python scripts/init_diagnosis_kb.py --reset
```

#### 坑 3：`await self.milvus_client.has_collection()`

`_ensure_connection` 里原来这么写：

```python
await self.milvus_client.has_collection(self.collection_name)
```

但 `has_collection` 是**同步方法**，await 一个 `bool` 会抛：

```
object bool can't be used in 'await' expression
```

每次连接检查都被误判为断开，触发无意义重连，日志刷屏。

**解决方案**：去掉 `await`：

```python
self.milvus_client.has_collection(self.collection_name)
```

#### 坑 4：空文档也生成占位 chunk

最初只要页面字数少于阈值就生成图占位 chunk，导致纯空白 txt 也会生成 `"[架构图/流程图：第 1 页]"`。

**解决方案**：在 `process_document` 开头判断整份文档是否没有任何有效文本，是则直接返回空列表：

```python
total_text = "\n".join(p.get("text", "") for p in pages).strip()
if not total_text and not any(p.get("is_diagram") for p in pages):
    return []
```

#### 坑 5：`pytest-asyncio` 装饰器缺失

`tests/test_intention_agent.py` 里的测试函数是 `async def`，但没加 `@pytest.mark.asyncio`，pytest 直接报错：

```
async def functions are not natively supported.
```

**解决方案**：补装饰器和 `import pytest`。

### 3.5 RAG fallback 的阈值保护（收口时补充）

最初 IntentionAgent 的 RAG fallback 是无条件触发的：只要规则识别为 `generic_ticket_diagnosis`，就会用 RAG 结果重新推断 scenario。

但当前商户 PDF 几乎全是架构图，RAG 检索相似度只有 0.5 左右。如果无条件采纳，低质量检索反而可能把 generic 错判成具体场景，**降低准确率**。

**解决方案**：在 `config.RAG_CONFIG` 中增加开关和阈值：

```python
RAG_CONFIG = {
    "embedding_model": "data/models/bge-small-zh-v1.5",
    "enable_intention_fallback": True,
    "enable_resolution_evidence": True,
    "min_similarity_threshold": 0.55,
}
```

- `IntentionAgent`：只有 top1 相似度 ≥ 0.55 时才采纳 RAG 推断，否则保持 `generic_ticket_diagnosis`。
- `ResolutionAgent`：通过 `enable_resolution_evidence` 控制是否补充证据。
- kb_hints 仍可保留在 key_entities 中，用于 reasoning 参考，但不改变 scenario。

这样既保留了完整 RAG 框架，又避免低质量检索干扰现有规则链路。

## 四、记忆系统的三层结构思考

改造过程中把记忆拆成三层：

1. **短期工作单记忆（Redis）**：当前会话上下文，随对话轮次更新。
2. **中期商户画像（MySQL/Postgres）**：商户长期属性、历史工单摘要。
3. **长期诊断模式库（向量库）**：相似历史案例、根因模式。

与 Aligo 旅行情景记忆的区别：

- 旅行情景更关注"当前出差人偏好 + 差旅政策"。
- 工单诊断更关注"商户实体 + 故障模式 + 责任归属"。

实现上采用**最小修改**：保留原有短期记忆参数，新增 `merchant_profile` 和 `diagnosis_patterns` 两层，扩展 `MemoryManager` 而不重写。

## 六、通用经验

### 6.1 先让链路能跑，再优化细节

Batch 1 最开始是"骨架回归"：IntentionAgent -> OrchestrationAgent -> LazyAgentRegistry -> 专业 Agent 能跑通，再逐步把 loop 控制、trace、响应构造收口。

如果一开始就追求完美架构，很容易陷入大规模重构，风险不可控。

### 6.2 mock 不是坏事，关键是接口稳定

Batch 2 补齐 30 个原子 Skill 时，底层数据先用 mock。但接口（输入/输出字段、状态枚举）先定下来，后续换真实数据源时上层不用改。

### 6.3 测试要覆盖"不可用"场景

RAG 依赖很容易因为环境、模型缺失、Milvus 损坏而失败。测试里专门加了：

- RAG Agent 不可用时 IntentionAgent 仍能用规则识别。
- RAG Agent 不可用时 ResolutionAgent 仍能做归属判定。
- 真实依赖未安装时跳过向量库测试。

这比只测"Happy Path"有价值得多。

### 6.4 动态导入要谨慎处理 sys.path

`.claude/skills/ask-question/script/agent.py` 是通过 `importlib.util` 动态加载的，模块内部会 `import utils.xxx`、`from config import ...`。必须在加载前确保项目根目录在 `sys.path` 中：

```python
project_root = str(Path(__file__).parent.parent.absolute())
if project_root not in sys.path:
    sys.path.insert(0, project_root)
```

否则在不同目录下运行脚本时会报 `ModuleNotFoundError`。

## Batch 3.2：降级策略

### 1. Skill 超时与统一降级返回格式

生产环境里，单个 Skill 可能因为网络抖动、数据库慢查询或下游服务挂掉而卡住。如果 `tool_registry.execute` 没有超时控制，一个工具 hang 住就会拖垮整轮诊断。改造前 `execute` 只做了简单的 try/except，返回格式也不统一：有时 `{"error": ...}`，有时 `{"status": "not_found"}`，调用方很难判断。

改造方案：在 `config.RESILIENCE_CONFIG` 中增加 `skill_timeout_sec`（默认 5 秒），`execute` 内部用 `asyncio.wait_for` 包装 handler 调用。所有返回都统一为 `status + tool + message + data` 结构：成功是 `"success"`，超时是 `"timeout"`，异常是 `"error"`，未注册工具也是 `"error"`。对旧代码兼容：如果 handler 直接返回 `{"error": ...}`，会自动规范化。

这样做的好处是：所有 Skill 调用者只需检查 `result.get("status") == "success"`，超时和异常都能被统一识别。测试覆盖未注册工具、异常、超时、成功、旧格式五种情况。

### 2. 知识库不可用降级

`search_kb` 当前同时被 `run_search_history_ticket` 和 `run_search_policy_faq` 使用。RAG 依赖 Milvus Lite 和 sentence-transformers，初始化较重，失败时不应阻断业务 Skill 执行。

改造方案：在 `diagnosis_agents.py` 中增加 `_is_degraded(result)` 辅助函数。两个 search skill 在调用 `registry.execute("search_kb", ...)` 后，先判断状态是否为 `error` 或 `timeout`。若是，返回空的 `history_matches` / `policy_matches`，summary 提示 `"知识库检索不可用，已降级为纯业务证据"`，`tools_called` 标记为 `"search_kb(timeout)"` 或 `"search_kb(error)"`。

这样即使 RAG 整个不可用，CodeAgent / DataAgent 仍能从订单、资产、结算等真实数据源拿到证据，ResolutionAgent 也能基于业务事实做归因，只是少了历史经验参考。

### 3. 日志工具不可用降级

`trace_api` 是查询接口调用日志的工具，常用于判断退款回调是否成功、是否超时。日志服务（如 ELK）不稳定时，这个工具可能失败或超时。

改造方案：以 `run_order_code_path` 为例，原来同时依赖 `trace_api` 和 `check_config`。改造后分别检测两个工具的返回状态：

- 若 `trace_api` 失败但 `check_config` 正常，且退款开关开启，则 verdict 改为 `"代码链路无明显异常（日志缺失，基于配置推断）"`。
- 若 `check_config` 也失败，则返回 `"需进一步排查代码链路"`。

`run_order_data_path` 也做了类似处理：`check_data` 失败时数据路径证据降级；`trace_api` 失败时不判断回调超时，仅依赖跨表快照。

核心思路是：**多个独立证据源之间可以互相兜底**，而不是一个挂了全挂。

### 4. 主循环异常保护

改造前 `DiagnosisService.diagnose` 的主循环直接调用 `intention_agent.reply` 和 `orchestrator.reply`，如果任一 Agent 抛异常，整次诊断直接失败，用户看到的是 500 错误。

改造方案：

- `IntentionAgent` 失败时，捕获异常并使用 `_fallback_intention` 构造一个规则兜底意图：scenario 沿用当前已识别场景或 `generic_ticket_diagnosis`，schedule 固定调度四个专业 Agent。
- `OrchestrationAgent` 失败时，使用 `_fallback_round_result` 构造一个 `"partial_failure"` 的部分结果，包含一个 `status="degraded"` 的 OrchestrationAgent 节点，继续进入 `LoopDecider` 判断。

这样即使最外层的意图识别或编排挂了，系统仍能返回一个可解释的响应，而不是直接崩溃。

### 5. Trace 降级可视化

降级发生后，不仅要内部处理，还要让用户/运维看到哪个节点出了问题。

改造方案：`TraceCollector.record_agent` 的 `status` 字段支持 `"success" / "error" / "timeout" / "degraded"`。在 `DiagnosisService._record_trace` 中：

- 如果整轮状态为 `partial_failure` 或 `error`，或者单个 agent 的 `status` 为 `error` / `timeout`，则 trace 中该 agent 的 status 统一标记为 `"degraded"`。
- `tools_called` 中保留降级标记，如 `"query_order(timeout)"`、`"search_kb(error)"`。

`format_trace_sse` 已经能透传 status 字段，所以前端 SSE 面板无需改动即可看到降级节点。后续 Batch 4 前端面板只需把 `status == "degraded"` 的节点渲染成黄色/橙色即可。

## Batch 4：React + TypeScript + SSE 实时诊断追踪面板

### 1. 为什么选 Vite + 手写 CSS

Batch 4 需要把 `web/index.html` 静态 demo 升级成可展示多 Agent 协作过程的面板。技术选型上我刻意保持克制：Vite + React 18 + TypeScript，不引入 Ant Design、Tailwind 等 UI 库。

原因有三：一是项目目标不是“前端工程多复杂”，而是“把后端 Agent 协作链路可视化出来”；二是你是初学者，减少依赖能降低心智负担；三是 Vite 的 `proxy` 配置可以让前端开发时无缝代理到 `localhost:8000`，联调成本低。

手写 CSS 虽然比组件库慢，但所有样式都在 `index.css` 里一目了然，面试时也能讲清楚每个状态颜色是怎么定义的。

### 2. SSE 回放 vs 实时流

后端 `/api/v1/trace/stream/{trace_id}` 的实现是“回放式”：diagnose 执行完成后，trace 已经存到 `trace_repo`，SSE 只是把预先生成的 events 依次推送给前端。这和“边诊断边推送”的严格实时流不同。

我没有去改 `DiagnosisService` 做真正实时推送，因为那会引入 WebSocket/Queue 等复杂度，违背最小改动原则。前端通过在每个 SSE 事件之间加 250ms 延迟，营造出“逐步推进”的视觉效果，足够支撑演示和面试讲故事。

后续如果要真正实时，可以在 `TraceCollector` 里加一个事件队列，让 `DiagnosisService` 在 diagnose 过程中直接 yield 事件。

### 3. 状态颜色语义设计

面板用颜色直观表达 Agent 执行状态：

- **绿色**：`success`，表示该 Agent 正常完成。
- **黄色/橙色**：`degraded`，表示该 Agent 或某个 Skill 超时/失败但已降级，诊断仍继续。
- **红色**：`error` / `timeout`，表示该 Agent 遇到未恢复错误。
- **灰色**：`unknown`，用于兼容旧数据。

颜色同时体现在三点：Round 时间轴上的圆点、Agent 节点的左边框、状态徽章。这样一眼就能看出哪条路径有问题。`trace_collector.py` 的 `status` 字段已经支持这些值，前端只需按字段映射颜色。

### 4. 前后端联调踩坑

开发时前端跑在 `http://localhost:5173`，后端在 `http://localhost:8000`，直接 fetch 会触发 CORS。解决方式是在 `api/app.py` 中加 `CORSMiddleware`，允许 `localhost:5173` 访问。

生产/演示环境则通过 `npm run build` 生成 `frontend/dist/`，再用 FastAPI 的 `StaticFiles` 挂载到 `/panel`。这样用户只需启动后端，访问 `http://localhost:8000/panel` 就能看到面板。

还有一个坑是 Node 版本。当前环境 Node 是 14.x，Vite 5 要求 Node 18+。我把 Vite 降到 4.x（`^4.5.5`），TypeScript 降到 5.3.x，构建成功。这也说明做前端工程前要先确认本地 Node 版本。

### 5. 组件拆分思路

面板拆成四个组件：

- `DiagnosisInput`：输入框 + 示例快捷标签 + 诊断按钮。
- `AgentTimeline`：左侧时间线，按 Round 分组展示 Agent 节点。
- `DiagnosisConclusion`：右侧结论卡片，展示 scenario、status、责任方、根因、建议。
- `StatusBadge`：状态徽章，复用颜色逻辑。

`App.tsx` 负责状态管理：调用 `/diagnose` 拿到结果和 `trace_id`，再建立 SSE 连接逐步更新 `liveRounds`。诊断完成后，如果有完整 trace 就展示完整 trace，否则展示 liveRounds。

### 1. 配置管理：从 dict 到 pydantic-settings

之前 `config.py` 是纯 dict，LLM API Key、模型名、日志级别都硬编码在代码里，换环境要改源码。这次改成 `config/settings.py`，用 `pydantic-settings` 做分层配置：

**一个坑**：创建 `StreamHandler` 后忘了 `setFormatter()`，导致日志一直是默认格式。修复后 JSON/Readable 两种格式都验证通过。

## Batch 8：多 Agent 通信契约收口 + 架构收敛

### 1. 问题背景：受控模式下的通信脆弱性

这个项目是多 Agent 协作，但通信方式是**中心化编排（Orchestrator-Worker）+ `Msg` + JSON 字符串**，Agent 之间传的是自由 dict，字段靠约定、没有 Schema。这带来三类隐患，直接体现在了离线评测里：**端到端 8/10 失败全是「缺关键实体」**。

### 2. 问题可能暴露的业务场景

| 缺陷 | 暴露的业务场景 |
|---|---|
| 实体在多层 dict 传递中丢失 | `ticket_id`/`order_id`/`merchant_id` 掉了，查不到订单、归因到错误商户，诊断结论直接错误 |
| `_merge_round_result` 全量摊平 agent 输出 | 两个 agent 输出同名字段时静默覆盖，责任方/根因被错误字段顶掉，得出错误归因 |
| LoopDecider 用 `"不一致" in summary` 判断 | summary 写成「未发现跨表不一致」会被误判为有异常，触发多余 cross_verify；反之话术一改就不触发，漏掉真实矛盾 |
| `status` 有 8 种取值、降级信号散落 | 前端 SSE 面板按 status 渲染颜色时漏判，降级节点显示成正常绿色，运维误以为链路健康 |

### 3. P0：统一消息契约 + 结构化信号

新建 `context/diagnosis_state.py`，用 pydantic 定义两个模型：

- **`AgentResult`**：专业 Agent 的统一输出契约。用 `extra="allow"` 保留业务扩展字段，同时把 `status`、`degraded`、`inconsistency_found` 声明为显式字段。`degraded` 由 `model_validator` 根据 status 自动推导，下游不再需要枚举 8 种状态值。
- **`DiagnosisState`**：诊断黑板，集中 `query/ticket/facts/rounds`，替代散落在 `DiagnosisService` 里的 `state` dict。

接入点：

```python
# agents/diagnosis_agent_base.py
result = AgentResult(status=..., summary=..., **extra_data)
return Msg(name=self.name, content=json.dumps(result.to_dict(), ...))
```

同时删掉 `loop_decider.py` 里 `"不一致" in val` 的字符串匹配，只信任结构化的 `inconsistency_found` 字段——这是本次最明确的 bug：`"未发现跨表不一致"` 这种 summary 也会被 `"不一致"` 命中。

### 4. P1：显式合并 + 清理旧映射

- `_merge_round_result` 从「排除黑名单」重构为 `DiagnosisState.merge_round()`，排除字段集中成 `EXCLUDED_KEYS` 类常量，并补排除新增的 `degraded`，避免契约字段污染 facts。
- 清理 `LazyAgentRegistry._legacy_mapping` 里 4 个旅行场景旧映射（`preference`/`information_query`/`itinerary_planning`/`event_collection`），只保留工单诊断仍在用的 `rag_knowledge`、`memory_query`。

### 5. P2：诊断黑板

`DiagnosisService._diagnose_internal` 从手写 `state` dict 改为 `DiagnosisState`，跨轮事实合并、意图实体合并、轮次记录都收敛到模型方法里，读取方统一用 `state.facts` / `state.ticket` / `state.query`，不再出现 `state.get("collected_data", {}).get("facts", {})` 这类多层取值。

### 6. 回归验证

```
pytest tests/ --ignore=tests/test_skill_orchestration.py -q
# 108 passed
```

`test_skill_orchestration.py` 仍是 Batch 2 细粒度 skill 接入待办（7 个失败），与本次契约收口正交。

### 7. 架构收敛方向：确定性逻辑显性化（已完成）

**问题定性**：不是「过度设计」，是「抽象层错位」——确定性逻辑（`strategy_matrix` + `OrchestrationAgent` 的调度）已经写得很完整，但被塞进了两个 Agent 壳里，导致职责边界模糊。

三个错位点：

| 错位点 | 现状 | 收敛目标 |
|---|---|---|
| `OrchestrationAgent` | 继承 `AgentBase` 却零 LLM 调用，伪 agent | 改为普通类 `Scheduler`，不继承 AgentBase |
| `strategy_matrix.py` | 挂在 `DiagnosisIntentionAgent` 内部调用 | 独立成层，归属 Scheduler |
| `IntentionAgent` 双层 | 兼容壳 + 真实现两层 | 只留一层，纯 LLM 决策 |

补全后的目标架构：

```
User
  ↓
Intention Agent（LLM）          ← 场景识别 + 实体提取
  ↓ scenario / entities
Strategy Matrix（确定性）        ← scenario × round → schedule
  ↓ Schedule
Scheduler（确定性）              ← priority / dependency / 并发
  ↓
Code / Operation / Data（LLM）   ← 三路并行取数 + 复核
  ↓
Skill / Tool（确定性）           ← 查业务数据
  ↓ Results
  ┌────────────────────┐
  ▼                    ▼
LoopDecider（确定性）   ← 判断是否需要 cross_verify
  │ 需要 → 回到 Strategy Matrix（round N+1）
  ▼ 不需要
ResolutionAgent（LLM）           ← 汇总证据 + 判责
  ↓
Final Answer
```

收敛时必须认清的三个点（否则图与实现脱节）：

1. **多轮循环**：`LoopDecider` 决定是否进入 round 2/3，`Strategy Matrix` 是 `scenario × round` 二维规则表，不是单轮线性流程。
2. **Verification 是「确定性触发 + LLM 执行」混合**：`LoopDecider` 用确定性规则判断是否不一致，真正的跨表比对由 `DataAgent._order_round_two` 用 LLM 完成。
3. **Final Answer 由 `ResolutionAgent`（LLM）判责**，`responsible_party`/`root_cause` 不是确定性逻辑。

收敛步骤（3 步，全是现成逻辑重新归属，非重写）：

1. `OrchestrationAgent` 去壳 → `Scheduler`（普通类），保留 priority/asyncio/depends_on/skip_if_missing 全部确定性逻辑。
2. `strategy_matrix` 从 `DiagnosisIntentionAgent` 移到 `Scheduler` 持有，「scenario→schedule」职责显性化。
3. `IntentionAgent` 去兼容壳，只保留「LLM 场景识别 + 实体提取」，输出 `scenario + key_entities`。

成本：动 3 处调用关系 + 去壳，`strategy_matrix` 与调度逻辑一行不用重写。retry（当前缺失）与 timeout（散在 ToolRegistry/skill 层）的集中，留作去壳跑稳后的增量补齐。

**落地结果（2026-08-16）**：

1. `agents/scheduler.py` 新建，`Scheduler` 普通类持有 `StrategyMatrix`，不继承 AgentBase、不接收 Msg，直接 `run(intention_data) -> dict`。
2. `agents/diagnosis_intention_agent.py` 职责收缩为「场景识别 + 实体提取」，删除 `_build_schedule` 与 `agent_schedule` 输出。
3. 删除 `agents/intention_agent.py`（兼容壳）与 `agents/orchestration_agent.py`（伪 Agent）。
4. `services/diagnosis_service.py` 调用链切换为 `DiagnosisIntentionAgent -> Scheduler`。
5. 回归测试 107 passed；离线评测 44/44，五项指标均 100%，无降级。
