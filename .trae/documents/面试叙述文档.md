# 小哈工单智能诊断助手 — 面试叙述文档

> 用途：面试前 15 分钟结构化自述的底稿 + 追问预案。
> 核心命题贯穿全文：**在一个多 Agent 系统里，如何证明 LLM 真的在「决策」，而不是一个可有可无的摆设。**

---

## 0. 一句话定位（电梯陈述）

> 我从一个真实业务（商户工单诊断）抽象出一个「受控多 Agent」诊断系统，核心解决两个问题：一是**如何用评测证明 LLM 的介入有实际价值**，二是**如何划分 LLM 与确定性代码的职责边界**。最终用「三档自治梯度 + 黑板假设状态机 + 双态回归评测」这套架构，把端到端 Pass@1 从 77.27% 做到 100%，并用「关/开 LLM」的对照实验证明 LLM 不是摆设。

---

## 1. 项目背景

- **业务场景**：商户工单诊断（订单状态异常 / 资产分配失败 / 结算金额不符），需要多域证据交叉定位根因并判责。
- **技术形态**：Python 后端（FastAPI + AgentScope）+ React/TS 前端 SSE 追踪面板 + Milvus Lite RAG 知识库。
- **核心命题**：多 Agent 系统里 LLM 很容易变成「调用封装器」——绕一圈还是确定性规则在算。这个项目要回答「LLM 的介入到底带来了什么」。

---

## 2. 架构演进主线（4 个阶段）

> 这是面试的主叙事线，从 git 提交历史提炼，每个阶段都有明确的「为什么」。

| 阶段 | 时间 | 关键动作 | 驱动因素 |
|---|---|---|---|
| 1. 跑通闭环 | 07-31 ~ 08-09 | Multi-Agent Orchestration：Intention → Orchestration → Code/Operation/Data → Resolution | 先让完整链路能跑 |
| 2. 评测驱动 | 08-11 ~ 08-15 | 建离线评测 + 分环节命中率，定位瓶颈 | 基线 Pass@1 只有 77.27% |
| 3. 架构收敛 | 08-15 ~ 08-16 | OrchestrationAgent「去壳」→ 普通 Scheduler；StrategyMatrix 独立成层 | 发现「伪 Agent」，抽象层错位 |
| 4. 假设驱动 | 08-16 ~ 08-17 | 黑板假设状态机 + 三档自治梯度 + 双态回归 | 让 LLM 真正「决策」，并证明它有效 |

### 阶段 1：跑通闭环（Multi-Agent Orchestration）

最初按生产级 Multi-Agent Orchestration 搭：上层 IntentionAgent 做场景识别，中间 OrchestrationAgent 调度，下层 CodeAgent/OperationAgent/DataAgent 按排查路径拆解，ResolutionAgent 做交叉验证判责。

**为什么先这样**：验证完整链路能不能跑通，不追求架构完美。原则是「先跑通，再优化细节」。

### 阶段 2：评测驱动优化（77.27% → 100%）

补了离线评测，第一批基线 **Pass@1 = 77.27%（44 用例，10 个失败）**。

**关键转折**：一开始我直觉以为是 RAG 或记忆系统的问题，也确实从 RAG 侧做了 query/recall、重排、父文档召回、缓存等优化——**但没解决主要失败样本**。

于是给评测脚本加了「分环节命中率统计」，把链路切成 6 段（Intent → Entity → RAG → Tool → Agent → Verification），用数据定位到真正的瓶颈是 **Entity Resolution（实体解析）**，而不是 RAG：

- 原正则 `\b\d{4,6}\b` 在 Python Unicode 模式下把中文当单词字符，导致「商户2037」里的数字匹配不到。
- 「只有商户号、无订单号」时无法反查订单。

按「数据闭环」做了三阶段优化（商户名→ID、商户→订单反查、评测方法修正），每步都重跑评测量化验证：

```
Pass@1：77.27% → 81.82% → 86.36% → 90.91% → 100%
```

**收获**：用数据定位瓶颈、用评测闭环验证，远比凭直觉预判高效。之前做的 RAG 增强其实都没打在真正的瓶颈上。

### 阶段 3：架构收敛（去「伪 Agent」，确定性显性化）

数据闭环建立后，回头 review 编排代码，发现一个有意思的问题：**OrchestrationAgent 虽然继承了 AgentBase，但实际零 LLM 调用**——它做的就是 priority、depends_on、asyncio 并行和结果聚合；StrategyMatrix 里的 scenario→schedule 也是确定性规则。

也就是说，**LLM 决策和确定性编排实际上已经分离了，只是代码抽象层没有显性表达**。

所以没有推倒重写，而是做了一次「职责重新归属」：

- OrchestrationAgent 去壳 → 普通类 `Scheduler`（不再继承 AgentBase，不接收 Msg）。
- StrategyMatrix 从 IntentionAgent 内部独立出来，归 Scheduler 持有。
- IntentionAgent 收缩为「纯场景识别 + 实体提取」。

**核心原则**：**LLM 负责不确定性的理解和推理，确定性的策略与执行交给代码。**

**收获**：Agent 系统不应该为了 Multi-Agent 而 Multi-Agent。这次改动不是改变业务行为，而是「重新归属已有能力，降低不必要的 Agent 抽象」。改造后 107 个测试全过、离线评测 44/44 五项指标全 100%，证明没引入回归。

### 阶段 4：假设驱动动态调度（让 LLM 真正决策）

架构收敛后，进一步深化「LLM 到底该在哪些点决策」，产出三档自治梯度 + 黑板假设状态机（见下节）。并用**双态回归**证明 LLM 非摆设。

## 3. 核心设计决策（3 个，每个都有「为什么 + 代价」）

### 决策 1：三档自治梯度（不是「全上 LLM」）

| Agent | 自治档位 | LLM 的边界 |
|---|---|---|
| OperationAgent | 流程型（零 LLM） | 确定性业务流程，纯规则 |
| DataAgent | 受控解读型 | LLM **只归因不选工具**，且归因结果强制命中候选集 |
| CodeAgent | 探索型 | LLM 决定「深挖哪条链路、判什么根因」 |

**为什么**：工单诊断的证据链有「确定部分」（查什么数据、走什么流程）和「不确定部分」（异常该怎么解读、根因是什么）。全部上 LLM 是浪费和不可控，全部规则又无法泛化。按「不确定性」分层，把 LLM 精确投放到「需要理解推理」的环节。

**代价**：受控 LLM 需要强校验（DataAgent 的 `conflict_type` 必须命中候选集，越界丢弃），增加了约束代码。

### 决策 2：黑板 + 假设状态机（不是「各 Agent 拼结果」）

专业 Agent 产出 `hypothesis`（如 CodeAgent 产 `api_trace` 假设、DataAgent 产 `db_state` 假设），写进共享黑板 `facts["hypotheses"]`，状态机 `pending → verified/refuted`。下一轮由 `HypothesisRoutingRule` 扫描 pending 假设，路由到能验证该证据维度的 Agent，验证后写回状态。ResolutionAgent 最终从 verified 假设推导根因。

**为什么**：比「多个 Agent 各自返回结果再拼一起」多了一层「可追溯 + 可验证」。假设的提出、路由、验证、归因是一条完整闭环，每一步都留痕。

**代价**：引入了跨轮状态管理复杂度，以及「跨轮 vs 同轮」两条数据通道的时序问题（见踩坑 4）。

### 决策 3：双态回归评测（证明 LLM 非摆设）

在评测里加 `--llm-autonomy` 开关，用**确定性 MockLLM**（无真实 API 调用）模拟 LLM 决策，做「关/开 LLM」对照：

| 指标 | 关 LLM（规则） | 开 LLM（MockLLM） |
|---|---|---|
| 根因命中率 | 93.75% | **100%** |
| 端到端 Pass@1 | 93.75% | **100%** |
| LLM 动态决策 | 0% (0/4) | **100% (4/4)** |
| 失败用例 | 3 | **0** |

**为什么**：真实 LLM 不可复现、有成本、有延迟，无法在回归里跑。用「确定性 MockLLM + 双态开关」既保证可复现，又能严格证明「LLM 介入前动态 case 必然失败、介入后必然通过」——这是「LLM 非摆设」的量化证据，而不是「我觉得 LLM 有用」。

## 5. 高价值踩坑（按叙事线组织，每个都有「现象 → 定位 → 解决 → 收获」）

### 踩坑 1：OrchestrationAgent 是「伪 Agent」

- **现象**：继承 AgentBase 却零 LLM 调用，只做调度。
- **定位**：不是「过度设计」，是「抽象层错位」——确定性逻辑被塞进了 Agent 壳。
- **解决**：去壳成普通 `Scheduler`，StrategyMatrix 独立成层。
- **收获**：明确 LLM 决策边界，不为 Multi-Agent 而 Multi-Agent。

### 踩坑 2：评测驱动 vs 直觉预判

- **现象**：基线 77.27% 失败，直觉归因 RAG/记忆，做了大量 RAG 优化无效。
- **定位**：加「分环节命中率」，数据指向 Entity Resolution（Unicode 正则把中文当单词字符）。
- **解决**：三阶段实体解析优化，每步重跑评测。
- **收获**：**用数据定位瓶颈、用评测闭环验证，远比凭直觉高效**。

### 踩坑 3：responsible_party 的「证据维度映射」是错的

- **现象**：想从「假设 type」推导责任方，结果开 LLM 后 16 个用例失败。
- **定位**：`api_trace`（接口链路）被映射成「技术侧」，但 order 场景的「回调超时」责任方其实是「数据侧（后台脚本）」。
- **解决**：回退映射，只让 root_cause 从假设推导，responsible_party 保持场景级硬编码。
- **收获**：**root_cause 是「证据级」（假设 detail = 根因文本），responsible_party 是「场景级」（责任大类由场景决定）**——两个字段的分层不同，不能同构映射。

### 踩坑 4：previous_results vs facts 的时序

- **现象**：round 3 内归因层读不到 verified 假设。
- **定位**：`merge_round` 发生在整轮结束后，而 ResolutionAgent 在同轮内执行，此时 follow_up 写回的 verified 假设还在 `previous_results` 里，尚未 merge 进 `facts["hypotheses"]`。
- **解决**：归因层从 `previous_results` 读，而不是从 `facts` 读。
- **收获**：**「假设产生」写 `facts`（跨轮持久化），「假设验证结果」走 `previous_results`（同轮消费）——两条不同时序的通道。**

### 踩坑 5：RAG 的「低质量检索不如不检索」

- **现象**：RAG fallback 无条件触发时，相似度只有 0.5 的低质量检索反而把 generic 误判成具体场景，降低准确率。
- **解决**：加 `min_similarity_threshold=0.55`，低于阈值保持规则结果。
- **收获**：RAG 是「增强」不是「必须」，可用时用、不可用时降级，低质量时宁可不采纳。

## 6. 诚实的技术债 + 回答预案

> 面试官如果懂行，会顺着这些挖。主动点破比被动应对更专业。

| 已知局限 | 诚实回答口径 |
|---|---|
| 责任矩阵 score 是拍脑袋的（0.85/0.9/0.95 写死） | 「当前判责分数是规则硬编码的，还没有做成从证据动态计算。这是下一步要做『证据级判责』的地方，方向是把 conflict_type、inconsistency_found 等结构化信号接入打分。」 |
| 假设路由 / LLM 自主默认关闭 | 「能力是做了但默认关，因为 LLM 的准确率/成本/延迟还没在生产验证过，所以先保守地让规则路径兜底，开关留着渐进放量。」 |
| 真实 LLM 未验证（只用了 MockLLM） | 「双态回归用的是确定性 MockLLM，证明的是『LLM 决策链路有用』，不是『某个模型准确率高』。真实模型的评估是下一步。」 |
| 数据全是 mock | 「底层数据源先用 mock，但接口契约（输入输出字段、状态枚举）先定死，换真实数据源时上层不改。」 |

## 7. 15 分钟叙事脚本

1. **背景 + 命题（1 分钟）**：做什么、核心要回答「LLM 怎么才算有用」。
2. **第一版跑通（2 分钟）**：Multi-Agent Orchestration，为什么先跑通。
3. **评测驱动（3 分钟）**：基线 77.27% → 分环节命中率 → 定位 Entity Resolution → 100%。强调「用数据定位，不是直觉」。
4. **架构收敛（3 分钟）**：发现伪 Agent → 去壳 → 「LLM 管不确定、代码管确定」原则 → 107 测试 + 评测无回归。
5. **假设驱动 + 三档自治（4 分钟）**：黑板假设状态机、三档梯度、双态回归表格（93.75% vs 100%），收在「证明 LLM 非摆设」。
6. **踩坑 + 局限（2 分钟）**：挑 1-2 个有深度的踩坑（responsible_party 分层、时序），诚实讲已知局限和下一步。

## 8. 面试追问预案（Q&A）

- **Q：为什么不用单 Agent + 工具调用？** → 工单诊断需要多域证据交叉（代码链路/数据一致性/业务流程），单 Agent 的工具调用是线性的，无法表达「并行排查 → 假设 → 交叉验证」的协作结构；多 Agent 让职责和证据域一一对应。
- **Q：为什么不全部上 LLM？** → 成本 + 可控性。确定性环节（查什么、走什么流程）用 LLM 是浪费且不可复现，只有「异常解读」和「深挖决策」需要 LLM。三档自治梯度就是按不确定性投放。
- **Q：怎么保证 LLM 输出可靠？** → 受控 LLM 强校验：DataAgent 归因结果必须命中候选集，越界丢弃；CodeAgent 的根因走假设状态机，refuted 的不进归因；双态回归保证规则路径兜底。
- **Q：评测的 100% 是不是过拟合评测集？** → 有「分环节命中率」和「双态回归」两层防护：前者保证可归因，后者用「关/开 LLM」对照证明指标提升来自 LLM 决策而非刷分。同时评测集里专门留了「动态 case」验证 LLM 的不可替代性。
- **Q：这套架构的可扩展性？** → 假设类型是 6 维闭集（api_trace/db_state/config_state/biz_flow/policy/cross_verify），当前只激活 2 维，其余是扩展位；新增 Agent 走 LazyAgentRegistry 插件化，不改主链路。
