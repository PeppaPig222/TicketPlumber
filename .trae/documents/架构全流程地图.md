# 架构全流程地图（含文件功能清单）

> 从请求到响应的完整数据流，标注「已实现 ✅ / 未实现 ❌」，帮助建立项目全局认知。

---

## 一、主流程：请求 → 响应

```
用户/前端
  │  POST /api/v1/diagnose  { query, user_id, session_id }
  ▼
┌─ [API 层] FastAPI ─────────────────────────────────────────┐
│  trace_id middleware（注入 8 位 trace_id）                   │
│  每次请求新建 DiagnosisService（隔离多请求状态）              │
└────────────────────────────────────────────────────────────┘
  ▼
┌─ [主循环] DiagnosisService.diagnose()  for round in 1..3 ──┐
│                                                             │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 每轮固定四步：                                        │  │
│  │  ① IntentionAgent.reply()     意图识别                │  │
│  │  ② Scheduler.run()            按策略矩阵调度 Agent    │  │
│  │  ③ merge_round()              结果/假设写进黑板 facts │  │
│  │  ④ LoopDecider.decide()       决定 done/继续          │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
  ▼
[响应] 诊断结论 JSON + SSE 推送（agent_update/round_complete/diagnosis_complete）
       + Trace 落库（TraceRepository，可回放 /api/v1/trace/stream/{trace_id}）
```

**三轮的分工：**

| 轮次 | 意图命名 | 做什么 |
|---|---|---|
| Round 1 | `ticket_diagnosis` | 意图识别 + 基础信息收集（预热实体） |
| Round 2 | `deep_diagnosis` | 多域并行排查，产出假设（pending） |
| Round 3 | `cross_validate_and_resolve` | 假设验证（verified/refuted）+ 归因判责 |

## 二、意图识别（入口层）

```
query（工单描述 / 工单号）
  │
  ▼
IntentionAgent._build_entities()
  │
  ├─ ① _enrich_ticket：工单号 → query_ticket 工具反查工单（拿 issue_type）
  ├─ ② _detect_issue_type：关键词匹配「结算/资产/订单」
  ├─ ③ _scenario_from_issue：关键词 → scenario 闭集
  │      settlement_amount_mismatch / asset_allocation_failure /
  │      order_status_anomaly / generic_ticket_diagnosis
  ├─ ④ RAG fallback（仅 scenario==generic 时触发）
  │      search_knowledge → 相似度 ≥ 0.55 才用知识库文本辅助推断场景
  ├─ ⑤ 实体提取：ticket_id（WO-...）/ merchant_id（商户2037）/ order_id（ORD-...）
  │      + 反查（resolve_merchant / resolve_order）
  ▼
输出 intention = { scenario, key_entities, reasoning, intents, ticket }
```

**关键点**：意图识别是**纯规则 + RAG fallback**，不做 LLM 语义路由（场景闭集 + 第一道闸门）。

## 三、调度层（Scheduler + StrategyMatrix）——「策略选择与切换机制」

```
intention_data (scenario × round)
  │
  ▼
Scheduler.run()
  │
  ├─ _build_schedule：StrategyMatrix.build(ctx)
  │     ① 静态任务矩阵：scenario × round → 固定调度计划
  │     ② HypothesisRoutingRule：扫 pending 假设 → 追加验证 Agent
  │     ③ 合并去重（静态基线优先，不 override）
  │
  ├─ _filter_by_permissions：轮次权限白名单（防越权调度）
  │     Round 1/2: {Code, Operation, Data}
  │     Round 3:   {Code, Operation, Data, Resolution}
  │
  ├─ 注入 pending_hypotheses → facts（协作字段常驻白名单）
  │
  ├─ 按 priority 分组 → asyncio.gather 并行执行
  │     + depends_on（依赖）、skip_if_missing（实体门槛）
  │
  ├─ _build_role_context：Role-aware 上下文裁剪（每个 Agent 只看自己的事实域）
  │
  └─ _execute_agent：per-agent 超时（agent_timeout_sec=30）→ 超时标 degraded
```

**「策略选择」= StrategyMatrix（静态）+ HypothesisRouting（动态假设）**
**「切换机制」= 三态 Loop（轮间）+ 降级（LLM 挂切规则）+ 三档自治（不同不确定性用不同 LLM 策略）**

## 四、三个专业 Agent（三档自治梯度）

| Agent | 档位 | LLM 角色 | 作用 | 产出 |
|---|---|---|---|---|
| **CodeAgent** | 探索型 | LLM 决定深挖链路 + 判定根因 | 代码/日志/链路视角，追踪 API 调用链 | `api_trace` 假设 |
| **DataAgent** | 受控解读型 | LLM 只在候选集内归因（越界丢弃） | 数据一致性、跨表校验、标签冲突 | `db_state` 假设 |
| **OperationAgent** | 流程型 | 零 LLM，纯规则 | 权限/业务流程/政策校验 | 无假设，path_verdict |
| **ResolutionAgent** | 归因侧 | 无 LLM | 汇总 evidence + 判责 + root_cause | responsible_party + root_cause |

**三档核心逻辑**：按「任务不确定性」分配 LLM 决策权——闭集任务硬约束（DataAgent 候选集）、开放任务软约束（CodeAgent 假设状态机）、确定任务零 LLM（OperationAgent）。

## 五、Agent 间通信（黑板 + 结构化契约）

```
                    ┌─────────────────────────────┐
                    │  黑板 DiagnosisState.facts   │
                    │  （共享状态，唯一写入口）      │
                    └─────────────────────────────┘
                      ▲ 读           ▲ 写（集中收口）
                      │              │
        CodeAgent ────┤   DataAgent ─┼── OperationAgent
        （只读+返回）  │   （只读+返回）│   （只读+返回）
                      │              │
                      └── merge_round() 串行写回（唯一写入口）
```

**通信的三条规则（状态同步核心）：**

1. **Agent 无状态**：只读 facts、只返回结构化结果，不直接改共享态。
2. **集中写回收口**：所有写 facts 走 `merge_round` 串行做（避免并发写冲突）。
3. **结构化契约**：`AgentResult` 带 `hypothesis/hypotheses/path_verdict/evidence` 字段；假设用「6 维类型闭集 + 开放 detail」。

**双通道时序**：跨轮用 `facts`（轮间持久化），同轮用 `previous_results`（轮内传递，不经过 facts）——这是 Round 3 验证能读到 Round 2 假设的关键。

## 六、归因判责（ResolutionAgent）

```
Round 3 调度前：HypothesisRoutingRule 扫 pending 假设 → 路由到验证 Agent
  │
  ├─ priority1：CodeAgent/DataAgent/OperationAgent._follow_up()
  │    读 pending_hypotheses → 查证 → 写回 verified/refuted（在 previous_results）
  │
  └─ priority2：ResolutionAgent
       ├─ 读 previous_results 里 verified 假设 → root_cause（证据级，假设推导 ✅）
       └─ responsible_party（场景级，硬编码）
  ▼
Final Answer = root_cause + responsible_party + recommendations
```

## 七、评测体系（离线，scripts/run_evaluation.py）

```
core_eval_set.json（48 条，覆盖订单/资产/结算 + 长尾异常）
  │
  ▼
run_evaluation.py 自动化 Runner
  │
  ├─ 七段分环节命中率：Intent/Entity/RAG/Tool/Agent/Verification/LLM
  │    → 用数据定位瓶颈（而非凭直觉）
  ├─ 双态回归：--llm-autonomy 关/开
  │    关 LLM：93.75%（动态 case 0/4）
  │    开 LLM：100%（动态 case 4/4）→ 证明 LLM 决策不可替代
  └─ 输出 eval_report JSON + MD
```

| 层次 | 当前实现 | 目标 | 改动量 |

| DB / Storage（诊断结果/评测集/trace/反馈） | ✅ SQLite 单机落库 trace + 反馈 | PostgreSQL Cluster 多实例 | 中改（替换持久化载体） |

### 演进路径（结论）

- **逻辑核心（约 70%）**：已全部实现，一行不用改。
- **生产化外壳（约 30%）**：Redis / DB / 反馈闭环，是「替换载体 + 新增工程流程」，不是「改架构」。
- **已落地（单机可跑）**：SQLite 持久化（trace + 反馈）、Redis 缓存层（可降级）、反馈 API + 回灌脚本。
- **仍待生产化**：Redis 全量 State/Blackboard 缓存、PostgreSQL Cluster 多实例、反馈自动触发评测+改规则——这三者都在「多实例 / 有线上流量」时才真正需要。

**一句话：当前架构 = 目标架构的「逻辑核心」+「单机生产化外壳」，多实例化外壳（Redis 全量 / PG 集群 / 自动迭代）是「套上去」而非「重构」。**
